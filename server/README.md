# Izzy Clipz API

The small server behind the Izzy Clipz app and the Izzy Clipz Business owner app: live booking with each barber's calendar, the owner's schedule, time off and walk-ins, the shop's own products (photos in Vercel Blob), Google and Yelp reviews, in-person card payments with Stripe Terminal (Tap to Pay on iPhone), no-show protection (a card saved with Stripe Checkout when booking online, charged only if the client doesn't come or cancels less than an hour before, and only when the owner decides to), connecting the shop's own Stripe account from the Business app's Settings (Stripe Connect), and signing in to the website's Business area on a computer with a 6-digit code from the app.

TypeScript on Vercel Functions (Node 24), Postgres on Neon, region `pdx1`. One function (`api/index.ts`) serves every route through a small router, so the Hobby plan's 12-function limit never matters.

## Environment variables

Set them in the Vercel project (as **Sensitive**). For the scripts (`migrate`, `dev`, `smoke`, `privacy:*`), put them in `.env.local`: copy `.env.example`, or run `vercel env pull .env.local`. Real environment variables win over the file, and empty values count as unset.

| Variable | Needed for | Notes |
|---|---|---|
| `DATABASE_URL` | Everything that touches the database | Neon's **pooled** URL. Added by the Neon integration. The privacy tools (`npm run privacy:*`) use it too, with the Stripe variables below to delete saved cards. |
| `DATABASE_URL_UNPOOLED` | `npm run migrate` | Neon's direct URL (schema changes shouldn't go through PgBouncer). Added by the integration. |
| `OWNER_KEY` | Owner endpoints | At least 32 characters, or owner endpoints answer 503 `owner_not_configured`. Make one with `openssl rand -base64 48`. The owner pastes it into the Business app once. |
| `CRON_SECRET` | `GET /api/cron/daily` | Random, 16+ characters. Vercel Cron sends it as `Authorization: Bearer …`. Unset means the cron route always answers 401. |
| `BLOB_READ_WRITE_TOKEN` | Product photos | Added when a Blob store is connected (the SDK can also use the store's OIDC credentials). |
| `GOOGLE_PLACES_API_KEY` | Live Google reviews | Places API (New), restricted to that API. Unset: the app gets `available: false` and a Google Maps link. |
| `GOOGLE_PLACE_ID` | Google reviews | Default `ChIJGz5HChRv3IARYJJy_6jyRm8`. |
| `GOOGLE_DAILY_LIMIT` | Google reviews | Calls per shop-local day, default `30` (stays inside the 1,000 free calls a month). `0` turns Google off. With the website live, raise it before launch (see [Website](#website)). |
| `YELP_API_KEY` | Yelp reviews | **Leave it unset on the live server**: Yelp's API terms bar commercial use and Yelp ratings next to other reviews, so the shop's legal documents say the website and apps show only Google's reviews and link to Yelp (`docs/legal/research.md` §12.2). Unset: `available: false` and the Yelp page link, which the website and apps show as "Read our reviews on Yelp". Set it only with Yelp's written consent. |
| `YELP_BUSINESS_ID` | Yelp reviews | Default `izzy-clipz-barbershop-oceanside` (the alias works as an id). |
| `STRIPE_SECRET_KEY` | Payments, no-show protection | `sk_test_…` or `sk_live_…` (restricted `rk_` keys work too, with write access to PaymentIntents, Customers (deleting a saved card's Customer), Payment Methods (detaching a saved card) and Checkout Sessions, and in connect mode to Accounts, Account Links and Terminal Locations). Without `STRIPE_CONNECT` it's the **shop's own** account (direct mode). With `STRIPE_CONNECT=on` it's the app developer's **Connect platform** key, and the shop's own account is connected from Settings (see below). Unset: payment endpoints answer 503 `stripe_not_configured`, and online bookings need no card. Setting it does **not** turn no-show protection on: the owner does that in the Business app (Settings → No-show protection), once the app versions with the card screen are out. |
| `STRIPE_CONNECT` | Connecting the shop's own Stripe account | `on` turns connect mode on. Unset, or `off` (`false`, `0`, `no`, `none`, `disabled`, `direct`), keeps direct mode, as before; any other value also counts as on, so a typo can never treat the developer's platform key as the shop's own (the shop's card payments would land in the developer's account). Needs `PUBLIC_BASE_URL`. |
| `STRIPE_TERMINAL_LOCATION_ID` | Payments (direct mode) | `tml_…`. Passed to connection tokens; the Business app also needs it to connect Tap to Pay. Ignored in connect mode: the server makes the shop's location on its connected account. |
| `STRIPE_WEBHOOK_SECRET` | `POST /api/stripe/webhook` | `whsec_…` from the webhook endpoint for events on your own account. Optional: without it (and without the next one) the webhook answers 503 and `…/complete` is the only way payments get recorded. |
| `STRIPE_CONNECT_WEBHOOK_SECRET` | `POST /api/stripe/webhook` (connect mode) | `whsec_…` from the platform's **Connect** webhook endpoint (events on connected accounts). The webhook accepts a signature from either secret. Without it, a connected account's status is only refreshed when Settings is opened, and payments only by `…/complete`. |
| `PUBLIC_BASE_URL` | No-show protection; **required in connect mode** | The API's own https address (`https://izzy-clipz-api.vercel.app`), which is also the website's. Used for the pages Stripe Checkout and Stripe's onboarding send people back to (with a live key it must be https). Unset: card saving uses the address the request came in on, which is right as long as the apps use the production domain; connecting Stripe answers 503 until it's set. |
| `PG_POOL_MAX` | Optional | Pool size per function instance, default 5. |

## Local development

Node 22.12 or later (`.nvmrc` says 24, which is what Vercel runs).

```sh
cd server
npm ci
npm test              # vitest: everything, against PGlite (no database to install)
npx tsc --noEmit      # strict type check (also what `npm run build` does on Vercel)
```

To run the API itself:

```sh
DATABASE_URL=postgres://… OWNER_KEY=… npm run migrate   # once
DATABASE_URL=postgres://… OWNER_KEY=… npm run dev       # http://localhost:3000/api/health
```

`npm run dev` (`scripts/dev.ts`) serves the same app with the production dependencies over plain Node HTTP and reads `.env.local` if it exists, so it needs no Vercel login. `vercel dev` works too once the project is linked.

## Website

The shop's website lives in `web/` (Vite 6, React 18.3, TypeScript, React Router 6, every version pinned in `web/package-lock.json`): Home, Services, Barbers, Reviews, Visit, booking in five steps (with the card on file when the shop's no-show protection needs one), My appointments, and Izzy Clipz Business at `/business`: the owner signs in with a 6-digit code from the Business app (Settings → Use on a computer) and gets the day's schedule with checkout (cash and other payments; cards stay on the iPhone with Tap to Pay), analytics for the shop and each barber, products, and Settings (Stripe, no-show protection, the computers signed in). It installs as an app of its own. It reads the same API as the apps, from the same origin, so it needs no settings of its own. [`web/README.md`](web/README.md) has the details.

```sh
cd server
npm run build:web     # npm ci and build in web/: the site lands in public/
```

To work on it, run the API and the site's dev server side by side:

```sh
npm run dev                    # the API on http://localhost:3000 (above)
npm --prefix web ci            # once
npm --prefix web run dev       # the site on http://localhost:5173, /api proxied to :3000
```

To try the whole thing without a database or any keys, `npm --prefix web run build && npm --prefix web run serve:local` serves the built site and the real API on an in-memory PGlite (a new, empty database every start) at http://127.0.0.1:4173. That's also what the website's end-to-end tests run against (`npm --prefix web run e2e`).

The site is also a web app clients can install (Add to Home Screen on an iPhone, Install on Android, the install button in Chrome or Edge on a computer; `/app` shows how): a manifest, the icons, and a service worker (`/sw.js`, made by the build) that opens it offline. The worker keeps the site's own files and the public catalog, never anything from the API with a token or personal data, and a new version waits for the client to tap Reload. `vercel.json` serves `/sw.js` with `Cache-Control: no-cache`. A **demo version** (`npm --prefix web run build:demo`, into `web/dist-demo/`) answers the API in the browser from the shop's real catalog and hours, keeps its bookings in the browser, says it's a demo, and carries its own `vercel.json`, so it can be published as a static site of its own before this server is live. Publish it at the address this site will have (then every copy people installed becomes the real app with a tap on Reload), or, once this site is live elsewhere, deploy the retired demo (`npm --prefix web run build:retired`) in its place: never just delete it, since browsers keep opening their copy. [`web/README.md`](web/README.md) has the details.

On Vercel, `vercel.json` builds it (`buildCommand: npm run build:web`, `outputDirectory: public`) next to the API function in `api/`. Files on disk always win over rewrites, so `/assets/…`, `/robots.txt`, the icons, the share image and `/manifest.webmanifest` are served as they are; `/api/*` goes to the function; every other path that isn't a file gets `/index.html`, so `/book/time` or `/appointments` open the site at that page. A missing `/assets/…` file is a real 404. The hashed files under `/assets/` are cached for a year, and every page gets `X-Content-Type-Options: nosniff`, a referrer policy and `X-Frame-Options: DENY`. If `PUBLIC_BASE_URL` is set when the site is built, the share image in the Open Graph and Twitter tags gets that absolute address.

**Google reviews and the website.** The server never stores Google's reviews, so every visit that shows the rating (Home's reviews tile, when it comes into view, and the Reviews page) makes one Place Details call, and the default `GOOGLE_DAILY_LIMIT` of 30 a day was sized for the app alone. Past the limit, the website and the app both show the link to Google instead of the rating until midnight at the shop, so nothing breaks, but set a launch value: `100` allows up to about 3,000 calls a month, which is about $50 a month after the 1,000 free ones, at Google's $25 per 1,000 for Place Details with reviews (the Enterprise + Atmosphere SKU; check Google's current pricing before raising it further).

**Adding a card from the website.** Review asks `POST /api/cards/checkout` with `returnTo: "web"`, and the server's way back from Stripe's page (`/api/cards/return?session_id=…&to=web` and `/api/cards/cancel?to=web`) sends the browser to `/book/card-return?status=…`, where the site saves the card (`POST /api/cards`) and picks the booking up again from the tab's `sessionStorage`. The end-to-end tests go through the stand-in for Stripe's page in `web/e2e/serve.ts`, which follows the very URLs the server gave it, so they test that way back too. A saved card is kept with the number of the client who added it and only offered to that number, so on a shared computer nobody books with someone else's card.

## Tests

`npm test` runs every suite against **PGlite** (Postgres 18 compiled to WASM, with `btree_gist`), served over the Postgres wire protocol by `@electric-sql/pglite-socket`, so the production `pg` pool code runs unchanged. PGlite has one session, so the test pool has one connection and concurrent requests queue for it; the race tests still fire requests at the same moment.

To run the same tests against a **real Postgres** (true concurrency, pool of 5), point `TEST_DATABASE_URL` at a role that can create databases. Each test file gets its own throwaway database:

```sh
TEST_DATABASE_URL=postgres://postgres@127.0.0.1:5432/postgres npm test
```

CI (`.github/workflows/server.yml`) does both, on Ubuntu: PGlite on Node 22 and 24, and Postgres 17 on Node 24. ### Fixtures

- `data/catalog.json` and `test/fixtures/kit-slots.json` are generated from IzzyClipzKit, so the server books with exactly the app's menu, ids, hours and slot rules. Offering ids are the Kit's `Offering.id` (`<barber>/<squire item id>`); `firstAvailable` comes from `Catalog.firstAvailableOption(forService:)`; weekday keys are the Kit's `Weekday` (1 = Sunday … 7 = Saturday). The Kit's `CatalogExport` test fails if `catalog.json` drifts; regenerate it from the Kit, then run `npm run migrate` so the barber list follows.
- `test/fixtures/google/*.json` and `test/fixtures/yelp/*.json` follow the response formats in Google's Place Details (New) and Yelp's Places API reference. Their names and texts are obviously test data, not real reviews.
- `test/fixtures/no-show-rule.json` is the no-show fee rule (with the price cap), the policy wording, the clients' warning and the window labels for every menu price under several settings, plus late cancellations with their booking times (`lateCancels`, the 15-minute grace period) and the line for a time already inside the window (`notices`), written by `test/noshow-rule.test.ts`. The Kit's mirror of the rule (the Business app's settings preview, the booking notices) and the website's are checked against it.
- `test/fixtures/fee-cases.json` is which fee a booking can be charged (a no-show, a late cancellation, or none and the owner's message why), with each booking's start, end and booking time, whether each client's cancel time was late, the same at given moments (`clock`: the end of the appointment and the 7-day deadline), the deadline and grace period themselves, the warning before a late cancellation and the "Nothing was charged" answer, written by `test/feecase.test.ts`. The Kit's mirror (which charge button the Business app shows, the clients' warning and notice, and the fakes' answers) is checked against it.
- `test/fixtures/contract/*.json` are one example of every response type (and `errors/<code>.json` of every error code), written by the real handlers in `test/contract.test.ts` (sales and analytics: `test/contract-sales.test.ts`) after checking them against strict schemas of the contract. The Swift Kit decodes the same files. If a handler's output changes on purpose, regenerate them with `UPDATE_CONTRACT_FIXTURES=1 npm test` and commit the diff.
- `test/helpers/week.ts` makes a week of shop data through the real endpoints (bookings, checkouts by cash, other and card, products, time off, no-shows, a late cancellation and fees, across the November clock change); `analytics.json` and `analytics-barber.json` come from it, and `test/analytics.test.ts` lists every event and the numbers it adds up to.

### Smoke test after a deploy

```sh
npm run smoke -- https://izzy-clipz-api.vercel.app            # or SMOKE_BASE_URL
SMOKE_OWNER_KEY=… npm run smoke -- https://izzy-clipz-api.vercel.app
```

`scripts/smoke.ts` checks health, books the last start time of a day near the end of the 60-day window ("Smoke test", a 555-01xx number) with a manage token of its own (when that item needs a card for no-show protection, it first checks the policy and the warning clients see, and that booking it without one is turned down with `card_required`, then books an add-on that's included with a cut instead, which never needs a card), retries the booking with the same token and checks it gets the same appointment back, checks it left availability, reads it back with its manage token, cancels it and checks the slot came back. With `SMOKE_OWNER_KEY` (the server's `OWNER_KEY`; there's no separate test-only key) it also prints the no-show settings, checks the owner schedule and cancels through the owner API if anything fails midway. It also checks the website: the catalog (`/api/catalog`, with the shop's details), that `/` and a page like `/book/time` answer with the site's `index.html`, and that a missing `/assets/…` file is a real 404 (set `SMOKE_WEBSITE=off` against `npm run dev`, which serves only the API). `.github/workflows/server-smoke.yml` runs it by hand or after each successful production deployment, using the `API_BASE_URL` repository variable and the optional `SMOKE_OWNER_KEY` secret.

## Migrations

```sh
DATABASE_URL_UNPOOLED=postgres://… npm run migrate    # or with .env.local from `vercel env pull`
```

Applies `migrations/NNN_name.sql` in order, each in its own transaction, recorded with a checksum in `schema_migrations`. Running it again does nothing; two runs at once are serialized by an advisory lock. It refuses to continue if an applied file was edited: add a new numbered file instead. It then upserts the barbers from `data/catalog.json` (barbers no longer listed stay in the table, marked inactive, because old bookings point at them).

Run it once when the database is created, after every new migration, and after every catalog change. It isn't part of the Vercel build, so preview deployments can't change the production schema. That also means a new migration has to be applied **before** the code that needs it goes live: `002_manage_token_unique.sql` adds the `any_barber` column that every booking writes, `003_owner_idempotency_key.sql` the `idempotency_key_hash` column, and `004_no_show_protection.sql` the card and fee columns every booking writes, the `saved_cards` and `settings` tables and the payments' `kind` (with the late-cancellation window and the fee's reason), so a database without them can't take bookings or list payments. `005_stripe_connect_and_computers.sql` adds `stripe_connect_states`, `computer_codes`, `computer_sessions` and the `stripe_account_id` that every saved card and payment now writes, so run it **before deploying** this version, even in direct mode (owner auth reads `computer_sessions` for any request that isn't the owner key). All five only add things, so the code already live keeps working on the new schema: migrate first, then deploy.

`006_sales.sql` adds the `sales` and `sale_items` tables, `payments.sale_draft` (a card checkout's ticket) and, on appointments, the live sale (`sale_id`, `sale_total_cents`, `sale_method`) that every owner view of an appointment reads, so it too must be applied before the code that needs it: run 005 and 006 together, then deploy. Like the five before it, it only adds things: rows from before it stay valid, and the code already live ignores the new columns.

`007_payment_succeeded_at.sql` adds `payments.succeeded_at`, when Stripe says each payment went through (a card sale is sold then, a fee's `chargedAt` is then, and the analytics count a fee on that day), with the index the analytics read fees by. Every payment that succeeds now writes it, so apply it with 005 and 006, before deploying. It only adds a nullable column and an index: rows from before it keep `NULL` (a fee then counts on the day Stripe made it, as before), and the code already live keeps working.

`008_retention.sql` is what the legal documents promise: `appointments.completed_at` (a booking with a card on file that was completed can't become a no-show; filled in from `updated_at` for the ones completed before it), `anonymized_at` on appointments, sales and payments (with the indexes the daily job reads), and on `saved_cards` `removed_at` and `delete_requested_at`, its Stripe ids allowed to be empty once (and only once) a card is removed (`saved_cards_stripe_ids`); it also clears every `payments.receipt_email` kept so far. The new code writes `completed_at` and reads the rest, so apply 008 **before** deploying it. It only adds columns, an index or two and a check every existing row passes: the code already live keeps working on it (and any receipt email it still writes meanwhile is cleared by the next daily run).

## How it behaves

- **Times**: the API speaks UTC instants (`2026-11-02T18:00:00Z`, no fractional seconds) and shop-local days (`2026-11-02`). All day and hour math happens in the catalog's time zone (`America/Los_Angeles`) with Luxon, never in the server's own zone, so daylight saving changes are handled by tzdata.
- **Availability** follows the Kit's `BookingCalendar`: start times every 30 minutes from opening, ending by closing, at least 30 minutes from now, today through today + 60 days, minus the barber's booked or completed appointments and time off (theirs or the whole shop's). Every requested day is listed, with no slots when there's nothing to book. "Any barber" uses the catalog's `firstAvailable` offerings: a start is open when one of those barbers is free for their own item's length, and `barberIds` lists the free ones in team order.
- **Booking** is one transaction with no global lock: the barber rows are share-locked (time off takes them exclusively, so a booking and new time off can't interleave), time off is checked, and the exclusion constraint `appointments_no_overlap` rejects overlaps (`23P01` → 409 `slot_taken`). "Any barber" picks the free barber with the fewest live bookings that day, ties in team order, and moves to the next one if the constraint says it was just taken. Customers must pick one of the calendar's start times. The shop may book any minute inside opening hours, including "now" or earlier today, with no lead time; seconds are dropped.
- **Limits**: 5 booking attempts per IP per hour (counted in 10-minute buckets of a sliding hour, after the request passes validation; a retry of a booking that went through isn't an attempt; the IP is stored only as a hash), and 3 upcoming booked appointments per phone number (shop bookings count too). Both answer 429 `rate_limited`, with a message that says which limit it was and what helps (the apps show it as is: "Try again in an hour" for the IP limit, "Cancel one" for the phone limit). The shop's own bookings have no IP limit. Consider one Vercel WAF rate-limit rule on `/api/*` as an outer guard.
- **Manage tokens**: 32 random bytes, base64url (43 characters), returned once at booking. The app may make its own and send it as `X-Manage-Token` on `POST /api/appointments` (see safe retries); otherwise the server makes one. Only the SHA-256 is stored (unique per appointment) and it's compared in constant time. A missing `X-Manage-Token` is 401; a wrong token or unknown id is 404, so ids can't be probed. Customers can cancel until the appointment starts.
- **Safe retries**: the app's own manage token doubles as the booking's idempotency key, so a retry after a lost answer (a flaky mobile network) can't book twice or get `slot_taken` for the client's own appointment. If an appointment already has that token and the request asks for the same target in the same way (the same `offeringId`, or the same `serviceId` with `barberId: "any"`), the same start and the same phone number, the answer is 200 with `{ appointment, manageToken }` (the same token, the appointment as it is now, even if it has been cancelled since); the name, email and note aren't compared. The same token with other details is 400 `invalid_request` ("That booking token was already used."). A token that isn't exactly 32 bytes in canonical base64url is 400 too. Retries are answered before the time rules and the IP limit, so they work after the lead time has passed and once the hour's attempts are used up. Two copies of one request racing make one appointment: the unique index on `manage_token_hash` (or the barber's overlap constraint) stops the second insert, and it answers like a retry. Shop bookings ignore the header and use `Idempotency-Key` instead (below).
- **Safe retries for the shop**: the owner app sends an `Idempotency-Key` (32 random bytes in base64url, like a manage token) with each walk-in or phone booking, and the same one when the owner books it again after a lost answer. If an appointment the shop booked already has that key, for the same target asked the same way, the same start (to the minute), the same client name and the same phone number (or none), the answer is 200 with `{ appointment }` as it is now; the email and note aren't compared. The same key with other details is 400 `invalid_request` ("That booking key was already used for another booking."), and a malformed key is 400 too. Only the SHA-256 is stored (`idempotency_key_hash`, unique), and racing copies make one appointment, as above. Without the header, a repeated walk-in is booked again (for "any barber", in the next free chair).
- **Owner auth**: `Authorization: Bearer <OWNER_KEY>`, compared as SHA-256 digests in constant time, or `Bearer <a computer's session token>` (see signing in on a computer). Without a long enough `OWNER_KEY` every owner route answers 503 `owner_not_configured`; a missing, wrong, signed-out or expired credential is 401 `unauthorized`. Five routes take the owner key only, because only the Business app on the iPhone may use them: `POST /api/owner/computer-codes`, `DELETE /api/owner/stripe/connect`, `POST /api/owner/terminal/connection-token`, `POST /api/owner/payments` and `POST /api/owner/payments/:id/receipt` (Tap to Pay is iPhone-only). A computer gets 403 `forbidden` there.
- **Reviews**: Google is fetched live on every `GET /api/reviews` (field mask `rating,userRatingCount,reviews,googleMapsUri`) and passed through in Google's order; nothing from Google is stored, only our own daily call counter in `api_usage`. Over the daily limit, unconfigured or failing, Google comes back `available: false` with the Maps link; after a failure the server waits a minute before calling Google again (10 minutes for Yelp, serving its cached copy meanwhile), so a slow or broken API doesn't hold up every visitor. Yelp (only with a key) is cached in `yelp_cache`, refreshed when it's 12 hours old, served stale only while it's under 24 hours old (if Yelp is down), and deleted at 24 hours on every read. The daily cron also purges the whole Yelp cache, because a once-a-day job that runs up to an hour late can't otherwise bound how long an unread row sits; on Pro, change the cron to hourly to tighten that. Every response is `Cache-Control: no-store`.
- **Payments**: the server creates every PaymentIntent (`allowed_payment_method_types: ['card_present']`, `capture_method: 'automatic'`, USD), so the app can't change the amount. `POST /api/owner/payments/:id/complete` asks Stripe for the PaymentIntent (with its latest charge) and records its status; only `succeeded` marks the appointment paid (the paid amount is the sum of its succeeded payments), as of when the card went through: the charge's time, or the webhook event's (`payments.succeeded_at`), even when the app confirms it the next morning. The webhook does the same from Stripe's side, and a late event can't undo `succeeded` or `canceled`. Every Stripe error is logged (its type, code, param, status, request id and message, with keys and client secrets cut out). A Terminal location Stripe turns down when making a connection token (a test-mode `tml_…` with a live key, or a typo) answers 500 `server_error` naming `STRIPE_TERMINAL_LOCATION_ID`, and a key it turns down names `STRIPE_SECRET_KEY`; the owner app shows that message when Tap to Pay can't start. Only a payment Stripe doesn't have is a 404.
- **Receipts after a card payment** (California's Song-Beverly Credit Card Act, Civil Code §1747.08, bars asking for personal details that are recorded with a card payment): `POST /api/owner/payments` takes no email. An older app that still sends `receiptEmail` gets a 400 `invalid_request` ("Take the card payment without an email. Once it goes through, you can email the client a receipt."), so nothing is asked for or recorded before the card is tapped; an empty `receiptEmail` is ignored. Once the payment went through, staff may offer a receipt: `POST /api/owner/payments/:id/receipt` `{ "email": "…" }` (owner key only) sets `receipt_email` on that PaymentIntent at Stripe, on the account the payment was made on, and Stripe emails the receipt (setting it again sends a new one to the new address). It answers `{ payment }`. The server never stores the address (`payments.receipt_email` stays empty, and migration 008 cleared the ones kept before) and never logs it (Stripe's message for an address it turns down is left out of the log). 400 for a payment that hasn't gone through, for a fee, or for an address Stripe turns down ("Stripe didn't accept that email address. Check it and try again.").
- **Retention** (`src/retention.ts`, what the Privacy Policy promises): the daily job removes the client's name (it becomes "Name removed"), number, email and note, and the appointment's manage token, owner booking key and fee message, from every appointment that ended more than 12 months ago, except while a fee for it is still pending; the client's name and any void reason from sales more than 12 months old (a sale voided after that takes no reason); and the description, the client's name on the checkout ticket and any receipt email from payments more than 12 months old (a fee's description, which names only the service, the barber and the time, stays, and so do the ticket's items and appointment, which voiding another sale of that visit still needs). It works in batches of 1,000, oldest first, for at most about 20 seconds, and the next run carries on. `anonymized_at` says when. What was booked, when, the price, what happened, the fee and the agreed terms stay, so the analytics never change (they don't read names, numbers, emails or notes), and so does the evidence for a card dispute. The 12 months are `RETENTION_MONTHS`, in one place. Any receipt email older code writes is cleared the next day. Saved cards: see no-show protection below.
- **Privacy requests**: see the section below.
- **No-show protection** (card on file): see the section below.
- **Errors** always look like `{ "error": { "code": "slot_taken", "message": "Someone just booked that time. Pick another." } }`, with messages written for the person using the app. Unexpected failures are logged (no request bodies or personal data) and answer 500 `server_error`.

## No-show protection

The client's rules: when protection is on, every online booking needs a card, and nothing is charged at booking. Two cases can be charged, both the same fee, and **the owner decides each time** (nothing is charged automatically): a **no-show**, and a **late cancellation**, when the client cancels in the app less than 1 hour before the start. Cancelling earlier is free, and a cancellation by the shop is never charged. The fee starts at the full price of the booked service (100%), and it's **never more than the booked service's price**. In the Business app the owner changes it (a percentage of the service, 1–100%, or a flat amount, $0.50–$500, capped at each service's price), turns late-cancellation charges off or changes their window (30 minutes to 48 hours), or turns protection off. A fee can be charged only **within 7 days** of the appointment's start, a no-show only **once the appointment has ended**, a booking that was **completed** never becomes a no-show, and cancelling **within 15 minutes of booking** is always free (the shop's Cancellation & No-Show Policy, `docs/legal/cancellation-policy.md`, says the same). **Protection is off until the owner turns it on**: setting `STRIPE_SECRET_KEY` alone (say a test key, to try Tap to Pay) never changes how clients book, since Stripe's test-mode card page turns real cards down.

- **When it applies**: Stripe is set up (`STRIPE_SECRET_KEY`), the owner has turned it on, and the booked item has a fee of at least 50¢ (Stripe's smallest charge). Items included with a cut have none. Otherwise no card is asked for and booking works exactly as before. The shop's own bookings (walk-ins, phone) never need a card.
- **The fee rule** is in one place (`src/noshow.ts`): percent mode is `round(price × percent / 100)`, half up to the cent ("starting at" prices use the starting price); flat mode is the flat amount, but never more than the item's price (a $20 flat fee on a $5 service is $5; the Kit's preview and the website follow the same rule). The fee is worked out at booking, for the barber the booking lands with, and kept on the appointment, so changing the settings later never changes an existing booking's fee.
- **The policy and the warning**: `GET /api/no-show-policy` gives what the apps show. `policyText` is what the client agrees to, e.g. "No payment now. If you cancel less than 1 hour before your appointment, or don't come, Izzy Clipz may charge $40 (100% of the service) to this card. Cancelling in the app more than 1 hour before is free." (with late cancellations off: "If you don't come and haven't cancelled … Cancelling in the app before your appointment is free."). `warning` is the notice for the Pick a day and time step and Review: title "Full Service Cancellation & No-Show Fee" ("Late Cancellation & No-Show Fee" when the fee is less than the full price, "No-Show Fee" with late cancellations off) and message "Cancelling less than 1 hour before your appointment, or not showing up, may be charged the full service price ($40). Cancelling in the app more than 1 hour before is free." (it "may be charged", like the agreed policy's "may charge": the shop decides each time). `lateCancelWindowMinutes` is the window (`null` with late cancellations off). Bookings open 30 minutes ahead, less than the window, so a time that starts sooner than the window can be cancelled for free only for 15 minutes after it's booked (the grace period): for the time the client picks, the apps add "This time is less than 1 hour away, so cancelling it more than 15 minutes after booking may be charged $40." under the warning (the Kit's `NoShowPolicy.lateCancelNotice(start:now:)`; the server words it in `lateCancelNotice` and writes it to `no-show-rule.json`, so the Kit and the website say exactly the same). For "any barber" the amounts are the range of the barbers' fees ("$55–$60"). The app sends `policyText` back exactly with the booking (`noShowPolicy`); the server keeps it, the window it states and the consent time (the booking time) as the evidence for a dispute. If it's no longer the current policy for that booking (the owner just changed the fee or the window), the booking is a 409 `policy_changed` and the app shows the new policy.
- **Saving a card** uses Stripe Checkout in setup mode, so card numbers never reach the server or the apps. The app makes a card token (32 random bytes, base64url, like a manage token) and sends it as `X-Card-Token` to `POST /api/cards/checkout`; the server makes a Stripe Customer and a Checkout Session (`mode: setup`, cards only, the policy under the Save button, 60 minutes to finish) with the token's SHA-256 in its metadata, and answers with Stripe's URL. The app opens it in `ASWebAuthenticationSession` (callback scheme `izzyclipz`). Stripe returns to `GET /api/cards/return?session_id=…` (Checkout needs an https address), which redirects to `izzyclipz://card-saved?session_id=…`; Cancel on Stripe's page goes through `GET /api/cards/cancel` to `izzyclipz://card-cancelled` (and a return without a usable session id to `izzyclipz://card-failed`). The app then calls `POST /api/cards` with the session id and the same token: the server checks with Stripe that the session is one it made **for that token**, in setup mode and complete, and stores the card's brand, last 4 digits, expiry and Stripe ids under the token's SHA-256 (never the token). Saving again with the same token and session answers 200 with the same card, so a lost answer is safe; the same token for another session is a 400 (one token, one card); anyone who only knows the session id (it's in the return address) gets a 404, because they don't have the token. Both card endpoints allow 10 tries per network per hour (`rate_limited`), to blunt card testing.
- **Booking with the card**: `POST /api/appointments` with `X-Card-Token` and `noShowPolicy`. A missing or unknown card, a card that expires before the appointment's month, or a card saved in test mode once the shop uses a live key (or the other way round) is a 400 `card_required`, with a sentence saying which. These checks come before the booking-attempt limit, so they don't use up the network's attempts. A retry with the app's manage token (`X-Manage-Token`) is answered before any of this, as before: the card isn't part of "the same booking". One card can book any number of appointments, until it's removed (below): a removed card, or one the client asked to delete, is "We couldn't find your saved card. Add it again." A booking made without "Remember me" says so with `"keepCard": false`: the card is then marked for deletion (`delete_requested_at`) in the booking's own transaction, so it books nothing else and the daily job deletes it once no booking needs it, exactly as `DELETE /api/cards` would, but without a second request that a lost connection could stop. Left out (or `true`), the card is kept, as before; a booking that needs no card ignores it, as it ignores the card.
- **Cancelling** in the app works as before at any time before the start; the server keeps when the client cancelled (`customer_cancelled_at`, never cleared), to the whole second, as the JSON writes it (`noShowFee.customerCancelledAt`). The apps decide from that time whether a late-cancellation fee can be charged, so the server decides from the same one: a cancel that lands 400 ms inside the window reads as exactly 1 hour before, and is free everywhere. A request the status turns down (the shop had already marked the booking) still counts when it came before the start. **The first time counts**: a booking the client cancelled early, which the shop then reopened, stays free however late it is cancelled again. **Within 15 minutes of booking it's always free** (the grace period: exactly 15 minutes after is still free), which matters for a time booked when its window had already started. The customer app warns before a cancellation inside the window (after the grace period): "Cancelling now, less than 1 hour before your appointment, may be charged $40, the full service price." (just the amount when the fee is less than the service's price; `noShowFee.fullPrice` says which). **The server makes sure the client was told**, by its own clock (the phone's may be off, or the minute may turn while the dialog is open): inside the agreed window, a cancel without `{ "acceptLateCancelFee": true }` is a 409 `late_cancel_fee` whose message is that warning, and nothing changes; the app shows it with "Cancel appointment" / "Keep appointment" and sends it again with the flag. Outside the window, for a policy without late cancellations, or for a booking without a card, nothing is asked (the flag is ignored).
- **Which booking can be charged** (`src/feecase.ts`, only the booking's own agreed terms count, never today's settings):
  - a **late cancellation**: the booking is cancelled by the client, who cancelled less than the agreed window before the start (exactly 1 hour before is still free) and more than 15 minutes after booking, and the agreed policy had late cancellations in it. It can be charged right away. If the shop reopens it, it can't be charged any more.
  - a **no-show**: the booking is marked no-show, its **end** has passed (a client who comes before the end isn't a no-show), and the client never cancelled nor asked to. A booking with a card on file can't be marked a no-show before its end (409 `not_started`, "You can mark a no-show once the appointment has ended."; the code keeps its first name, so the apps' handling stays), so the client can still cancel or come.
  - **a completed booking stays completed**: a booking with a card on file that was marked completed or checked out can't be marked a no-show, even after it's reopened (409 `already_completed`, "This appointment was marked completed, so it can't become a no-show."): the client came. `appointments.completed_at` (migration 008) keeps the first time it was completed.
  - **within 7 days**: no new try is sent more than 7 days (of 24 hours) after the start ("It's more than 7 days after the appointment, so the fee can't be charged."; exactly 7 days after still counts). A try whose answer was lost is still looked up at Stripe after that, and settled as not charged when Stripe never got it ("Nothing was charged. It's more than 7 days after the appointment, so the fee can't be charged.").
  - anything else is a 409 `not_chargeable` that says why: "The client cancelled at least 1 hour before, so there's no fee.", "The client cancelled within 15 minutes of booking, so there's no fee.", "The client cancelled this booking in the app, so there's no fee.", "The shop cancelled this booking, so there's no fee.", "The appointment is marked completed, so there's no fee to charge.", "Mark the appointment as a no-show first." (or the deadline's message once it's past), "The appointment hasn't ended yet, so it can't be a no-show.", "This booking has no card on file, so there's no fee to charge.", "The client's saved card was deleted, so it can't be charged."
  - The rule at a given moment is `feeCaseAt` (`src/feecase.ts`); the Kit's `Appointment.feeCase(at:)`, `chargeableFee(at:)`, `feeDeadline` and `noShowMarkRefusal(at:)` follow it (checked against `fee-cases.json`).
  - `appointment.noShowFee.reason` says which case it is: `"noShow"`, `"lateCancel"`, or `null` when neither applies (once the shop tried to charge it, what that charge was for, unless that try was settled as not charged).
- **Charging** (`POST /api/owner/appointments/:id/no-show-fee`, owner key, for either case): the server creates and confirms an off-session PaymentIntent (`off_session: true`, `confirm: true`, the Customer and card saved at booking, `allowed_payment_method_types: ['card']`, the stored fee in USD, description "No-show fee: …" or "Late cancellation fee: …", metadata `{ kind: "no_show_fee" | "late_cancel_fee", appointment_id, attempt }`) with the Stripe idempotency key `izzy-no-show-fee-<appointment id>-<attempt>`. While it decides, the appointment row is locked, so the fee is charged at most once: once it's `charged`, charging again answers the same appointment without calling Stripe. A try whose answer was lost (a timeout, an outage) leaves the fee `pending`; the next try first asks Stripe for that attempt's PaymentIntent (`paymentIntents.list` for the card's own Customer, created since the attempt began, matched by metadata), because Stripe may forget an idempotency key after 24 hours and a reused key would then charge again. Only if Stripe has none is the request sent again, with the same key. If Stripe has none and the booking can't be charged any more (the shop reopened it, or the client walked in late and the visit was completed), nothing was charged: the fee goes back to `none` (so it never shows as pending on a completed visit) and the answer is a 409 `not_chargeable` that says so, then why there's no fee now ("Nothing was charged. Mark the appointment as a no-show first."). That try is kept: charging later (marked a no-show again) picks it up first, looked up at Stripe and sent with the same key, so a request of it that reached Stripe late is never charged twice. A `pending` fee Stripe is still processing is looked up again instead. The Kit offers "Check again" on any `pending` fee, whatever the booking's status (`Appointment.chargeableFee(at:)`, `isFeePending`). Only a definite "no" from Stripe (`declined`, or `needsAction` when the bank wants the client to approve it, which an off-session charge can't do) lets the next try make a new PaymentIntent. Every answer is 200 with `{ appointment }`; `appointment.noShowFee.status` says what happened and `message` why, in plain words for the owner ("The card was declined: there isn't enough money on it."; never "lost" or "stolen"). Only a PaymentIntent Stripe reports as `succeeded` makes the fee `charged`.
- **Checking a fee** with `POST /api/owner/payments/:id/complete` (as for in-person payments) works too: it updates the fee from Stripe, and still never marks the appointment paid.
- **Payments**: every fee PaymentIntent is in `payments` with `kind: "noShowFee"` or `"lateCancelFee"`, so Payments today lists it as such (with Stripe's status), on the day Stripe made it. A fee is not a payment for the service: it never marks the appointment paid, and the paid amount only adds up in-person payments. Its `chargedAt` is when Stripe says it went through (the charge's time, or the webhook event's), which is also the day it counts in the analytics, even when Stripe finished it days after it was tried.
- **The webhook** keeps fees right for answers that come later: `payment_intent.succeeded` makes the fee charged (any fee PaymentIntent of that appointment, even an older attempt's, since money moved), failures and cancellations make the current attempt declined (or `needsAction` when Stripe's `last_payment_error` is `authentication_required`), a late "processing" can't undo a decline, and nothing undoes charged. A fee PaymentIntent the server never got to write down (it stopped right after Stripe charged) is found by its metadata and recorded.
- **Refunds and disputes**: reopening a charged appointment doesn't refund it; refunds are made in the Stripe Dashboard. The stored policy text (with its window) and consent time are the evidence if a client disputes a fee.
- **Removing a saved card** (`DELETE /api/cards`, with `X-Card-Token`): the apps call it from "Remove card", "Forget my details" and "Forget me", and right after a booking made without "Remember me" (which the website and the customer app also say in the booking itself, with `keepCard: false`). When no booking needs the card any more (one that's upcoming, can still be charged a fee within the 7 days, being still booked, a no-show or a late cancellation, or has a fee pending), the server detaches it (`paymentMethods.detach`) and deletes its Stripe Customer (`customers.del`; each saved card has its own), on the account it was saved on, and answers `{ "cardDeletion": { "status": "deleted", "message": "Your saved card is deleted. It can't be charged any more." } }`. Otherwise it marks it (`delete_requested_at`) and answers `"scheduled"` ("Your card will be deleted as soon as your appointments no longer need it."); so it does when Stripe doesn't answer. Either way the card can't book again, and calling it again answers the same; a token with no card is a 404. Stripe can't delete the completed Checkout Session, which keeps the email typed on Stripe's page; the Privacy Policy says so.
- **The daily job deletes saved cards that are due**: expired ones (after their expiry month, shop time), ones not used for a booking for 12 months (counting from when they were saved), and marked ones, once no booking needs them. A card on a Stripe account this server can't use any more (saved with the shop's own key before Stripe was connected, or the other way round, or after the shop took the platform's access away) can't be charged from here either: it's marked removed and logged, to be deleted in that account's Dashboard. A removed card keeps its row (old appointments name its brand and last 4), without Stripe's ids (`removed_at`).
- **Privacy**: only the card's brand, last 4 digits, expiry and Stripe ids are stored, until the card is removed.

**Costs** (Stripe, US): a no-show or late-cancellation fee is a card-not-present charge at Stripe's online rate, 2.9% + 30¢ (a $40 fee nets about $38.54). Saving a card costs nothing. A dispute costs $15, which Stripe keeps either way; countering it costs another $15, returned if the shop wins.

## Privacy requests

The Privacy Policy offers every client a copy of their information (including the cancellation terms they agreed to), corrections and deletion. Once the shop has checked it's them (by calling or texting the number on file), the owner runs, in `server/` with `DATABASE_URL` (and the Stripe variables, to delete saved cards) in the environment or `.env.local`:

```sh
npm run privacy:find -- --phone "(442) 555-0170"            # or --email client@example.com; --out request.json saves it
npm run privacy:correct -- --appointment <id> --name "Andre Sample" --phone "(442) 555-0170" --email ""
npm run privacy:forget -- --phone "(442) 555-0170" --dry-run  # shows what it would do; without --dry-run it does it
```

- **find** prints, as JSON, everything kept about the person who booked with that mobile number (written any way) or email (any case): their appointments, each with the exact no-show terms they agreed to (`noShowPolicy`) and when (`noShowConsentAt`); the checkouts (sales), card payments and fees of those appointments; and the cards saved for them (type, last 4, expiry, and whether and when it was deleted; the shop never has the number). Only what's linked to their own appointments is included, so another client's data never ends up in someone's copy; a walk-in sale with only a typed name can't be found this way. `--out` writes the file readable by the owner only.
- **correct** fixes a typo in an appointment's name, number or email (`""` removes the number or email), and the same name where its checkout copied it: on its sale and on a card checkout's ticket (`salesCorrected`, `cardTicketsCorrected`); a name typed differently at the checkout stays. It refuses an appointment whose details were already removed.
- **forget** removes the person's name, number, email and notes right away, as the daily job does after 12 months, from their appointments and those appointments' checkouts and card payments, except appointments still needed: upcoming ones, and ones whose fee is pending or can still be charged within the 7 days. It lists those (`kept`, with why) and says when to run it again (`runAgainAfter`). It also deletes their saved cards at Stripe, or marks them to be deleted as soon as no booking needs them, as `DELETE /api/cards` does. Stripe keeps its own records of payments (and the card page's record of the email typed there), as the Privacy Policy says.

The work is in `src/privacy.ts` (with the command line, so `test/privacy.test.ts` covers both); `scripts/privacy.ts` only connects it to the database.

## The shop's own Stripe account (Stripe Connect)

With `STRIPE_CONNECT=on`, the owner connects the shop's own Stripe account in the Business app (Settings → **Connect Stripe**): a Stripe window opens, he signs in or signs up and finishes Stripe's setup, and back in the app Settings says "Connected". From then on Tap to Pay, saved cards and no-show or late-cancellation fees all go to **his** account: he pays Stripe's fees, gets the payouts, and sees everything in his own Stripe Dashboard. The server's key belongs to the app's developer (the Connect platform), which only creates and reads the shop's account.

This is Stripe Connect with **Account Links** onboarding (Stripe's recommendation for new platforms; OAuth for Standard accounts is legacy), with an account made through Accounts v1 and controller properties, like a Standard account (Terminal fully supports it): the full Stripe Dashboard (`controller.stripe_dashboard.type: full`), the shop pays Stripe's fees (`fees.payer: account`), Stripe covers losses (`losses.payments: stripe`) and collects what it needs (`requirement_collection: stripe`), country US, the shop's name, barber-shop category (MCC 7241), website (`PUBLIC_BASE_URL`) and phone. It asks for the `card_payments` capability (Tap to Pay and direct charges need it active) with `transfers`, which Stripe wants requested alongside it. Charges are **direct charges**: every call for the shop is made on its account (the `Stripe-Account` header).

### Setting up the platform (the app's developer, once)

1. In the Stripe Dashboard of **your** account (the developer's, not the shop's), open **Connect** and finish getting started as a platform (the platform profile: connected businesses take their own payments directly, and Stripe handles risk).
2. Under **Settings → Connect**, set the **branding**: the name ("Izzy Clipz"), the icon and the color. Stripe's onboarding shows them, and won't open without them.
3. On the server, set `STRIPE_SECRET_KEY` to **your platform's** secret key (`sk_test_…` while testing, then `sk_live_…`), `STRIPE_CONNECT=on` and `PUBLIC_BASE_URL` (the production https address). `STRIPE_TERMINAL_LOCATION_ID` isn't used in this mode. Run `npm run migrate`, then redeploy.
4. In **Workbench → Webhooks**, add an event destination with **Events from: Connected accounts** (snapshot events, API version `2026-10-28.endive`, stripe-node 23's) at `https://<domain>/api/stripe/webhook`, for `account.updated`, `account.application.deauthorized`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `payment_intent.processing` and `payment_intent.requires_action`. Copy its signing secret (`whsec_…`) into `STRIPE_CONNECT_WEBHOOK_SECRET` and redeploy. (A destination for events from your own account, with `STRIPE_WEBHOOK_SECRET`, isn't needed in this mode; the webhook accepts either.) A live destination also gets the connected accounts' test-mode events (a test payment in the shop's Dashboard, `stripe trigger`); the server ignores every event whose mode (test or live) isn't its key's.
5. Test with the test key: in Settings, tap Connect Stripe, and use Stripe's test data in the onboarding. A test-mode connection doesn't count once the key is live: the owner connects again with the live key. Each mode keeps its own connection, so putting the test key back later (and tapping Connect Stripe) never replaces the live account: it's the shop's again as soon as the live key is back.

### What the owner sees

Settings asks `GET /api/owner/stripe`, which reads the account live from Stripe (and caches it; `account.updated` keeps the cache fresh too):

| `status` | When | `message` |
|---|---|---|
| `notConnected` | No account connected yet | Connect your Stripe account to take card payments in the app. |
| `needsInfo` | Stripe's setup isn't finished, or Stripe needs more information | Finish setting up Stripe to take card payments. |
| `pending` | Everything's sent and Stripe is checking it | Stripe is checking your details. This usually takes a few minutes. |
| `active` | Card payments are on | Connected. Card payments are on. Payouts to your bank are on. (or: Add your bank in Stripe to get paid out.) |
| `restricted` | Stripe paused the account for another reason | Stripe paused card payments: open Stripe to fix it. |
| `direct` | The server uses its own key (direct mode) | Card payments use this server's own Stripe key. |
| `off` | No Stripe key on the server | Stripe isn't set up on the server. |

Until the status is `active`, everything about cards behaves as if Stripe were off: Tap to Pay and new payments answer 503 `stripe_not_configured` with the status message for the owner ("Connect Stripe in Settings to take card payments." before connecting), the clients' card routes answer exactly as when Stripe is off, no booking needs a card, and the no-show policy says `required: false`. `dashboardUrl` (`https://dashboard.stripe.com/`) is where the owner signs in to his Dashboard.

Once it's `active`, Tap to Pay takes payments into his own account. The first time the Business app connects Tap to Pay with that account, Apple asks him once more to accept its Tap to Pay terms with the shop's Apple ID: Apple asks every Stripe account that takes its own payments (direct charges) to accept them for itself, and never asks again for that account, on any iPhone.

**Disconnecting** (`DELETE /api/owner/stripe/connect`, the owner key only) forgets the account that works with the server's key (a connection of the other mode, kept aside, stays); it stays open at Stripe, with its payments and payouts, and the answer says so. Connecting again sets up a new account. If the shop takes the platform's access away from its own Stripe Dashboard (`account.application.deauthorized`, or Stripe answering that it has no access to the account to the key that made it or last read it), the account is forgotten the same way, and Settings asks to connect again. Stripe gives the same answer to a key of any other Stripe account, so with a different key (say, one put on the server by mistake) the account is kept: Settings shows the last status, the log says so, and once the right key is back everything works as before, cards included. Cards saved on the old account can't book any more (`card_required`: "Add your card again: the shop changed its payment account.") and their fees can't be charged (`not_chargeable`: "This card was saved with the shop's old Stripe account."); payments and fees made on it are still looked up there. Payments and fees made with the shop's own key before connect mode (direct mode, no account stored) are on its own Stripe account, which the platform's key can't see: checking one answers where to look (a 404, or `not_chargeable` for a fee), and a fee whose answer was lost stays pending instead of being settled as not charged.

### How it works

- **Connecting**: `POST /api/owner/stripe/connect` `{ "returnTo": "app" | "web" }` (the owner key or a computer; no body means the app) makes the account on first use, never twice: an advisory lock serializes it, the id is stored before any link is made, and Stripe gets an idempotency key per mode and per connection (`izzy-clipz-shop-account-test-0`; the number goes up with each disconnect), so a try whose answer was lost gets the same account when it's tried again. It then makes an Account Link (`account_onboarding`, `collection_options.fields: eventually_due`) and a one-time state, and answers 201 `{ url, expiresAt }`. In direct or off mode it's a 409 `stripe_connect_off`.
- **The way back**: the link's `return_url` is `<PUBLIC_BASE_URL>/api/stripe/connect/return?state=…` and its `refresh_url` `…/refresh?state=…`, each with a state of its own: 32 random bytes in base64url, of which only the SHA-256 is kept (`stripe_connect_states`, hashed so that one page's state never works on the other), for an hour. The return page's state can be loaded more than once until then; the refresh page's works once. The return page reads the account's status from Stripe, then redirects (302) to `izzyclipzbusiness://stripe-connected?status=<status>` (the app) or `<PUBLIC_BASE_URL>/business/settings?stripe=<status>` (the website). The refresh page (Stripe sends the browser there when a link expired or was used) makes a new link and new states with the same way back, and redirects to Stripe; so the return address left in a browser's history after onboarding can never get anyone a link into the shop's Stripe account. An unknown, used or expired state gets a small page (400, never cached): "This link has expired. Go back to Izzy Clipz Business and tap Connect Stripe again." Both pages allow 20 visits per network per 10 minutes.
- **The cache**: the `stripe_connect` setting holds `{ accountId, livemode, keyFingerprint, connectedAt, locationId, chargesEnabled, payoutsEnabled, detailsSubmitted, requirementsDue, disabledReason, businessName, checkedAt }`. `livemode` is the key's mode when it was connected, and `keyFingerprint` (the start of the key's SHA-256, never the key) the key that made the account or last read it. A connection made while the key had the other mode is kept under `stripe_connect_other_mode` (at most one per mode), and is the shop's again when that mode's key is back.
- **Every call goes to the shop's account**: `shopStripe()` (`src/stripeaccount.ts`) is the one way to get a Stripe client for the shop and `requestOptions()` the one way to send its account, and a test walks every call site to check it. Connection tokens are made on it with its `location`; the Terminal location ("Izzy Clipz Barbershop" at 1919 Mission Ave, Ste 105, Oceanside, CA 92058) is made on it once the account is found able to take card payments (a status refresh: Settings, the way back from Stripe, or `account.updated`), or at the latest by the first connection token, once, and cached; if it's deleted in the Dashboard, the next try makes a new one. `GET /api/owner/me` only reads the cache, so the app finds the location there without the server asking Stripe. PaymentIntents are made, read and charged on it; payments keep the account (`payments.stripe_account_id`) and are always read back there. Customers and Checkout Sessions for saved cards are made on it; a card keeps its account (`saved_cards.stripe_account_id`), and is usable only while that account and its mode (test or live) are the shop's current ones. Fees are charged on the card's own account.
- **The webhook** takes a signature from either secret. An event of the other mode than the key (test or live) is answered 200 and ignored. An event with `account` (from a connected account) counts only for the shop's account now, the account its payment was made on, or (a fee the server never wrote down) the account its card was saved on; any other account's event is answered 200 and ignored. `account.updated` for the shop's account reads its status from Stripe (not from the event, since events can come out of order) and caches it; a Stripe failure answers 500, so Stripe sends it again. `account.application.deauthorized` for it forgets the account. The `payment_intent.*` events work as before.

## Signing in on a computer

The website's Business area works on a computer without typing the owner key there:

1. In the Business app, Settings → **Use on a computer** shows a 6-digit code (`POST /api/owner/computer-codes`, the owner key only, so a computer can't make codes). It works once, for 10 minutes, and a new code replaces the last one. Only an HMAC of it, keyed with the owner key, is stored.
2. On the website, the owner types the code (spaces and dashes don't matter) and the website sends it with a name for the computer, like "Chrome on Mac" (`POST /api/computer-sessions`). The answer is 201 `{ token, session }`: a session token (43 characters of base64url: 16 random bytes and the owner key's HMAC of them; only its SHA-256 is stored) that lasts 30 days. A wrong, used or expired code is 400 `wrong_code` ("That code isn't right or has run out. Open Izzy Clipz Business → Settings → Use on a computer for a new one."). Each network gets 10 tries per 10 minutes (then 429), and 5 wrong tries from anywhere burn the code.
3. The website sends `Authorization: Bearer <token>` like the owner key. It works on every owner route except the four iPhone-only ones (see owner auth). Its last use is written at most every 10 minutes.
4. `GET /api/owner/computer-sessions` lists the computers signed in (`current` marks the one asking); `DELETE /api/owner/computer-sessions/:id` signs one out, `DELETE /api/owner/computer-sessions` all of them, and `DELETE /api/owner/computer-sessions/current` the computer asking (the website's Sign out). Setting a new `OWNER_KEY` (say, after it leaked) signs every computer out, and makes any code from the old key stop working, since tokens and codes are sealed with it; the list then shows only computers signed in with the new key.

### Contract details worth knowing

- `POST /api/appointments` takes an optional `X-Manage-Token` header (the app's own manage token, 32 random bytes in base64url) and answers 201 for a new booking or 200 for a retry of one that went through (see safe retries above). Without it, nothing changes.
- `POST /api/appointments/:id/cancel` takes an optional JSON body `{ "acceptLateCancelFee": true }` (no body, or `{}`, is fine): the client agreed to the late-cancellation warning. Without it, a cancellation inside the agreed window is a 409 `late_cancel_fee` (see Cancelling under no-show protection).
- `POST /api/owner/appointments` takes an optional `Idempotency-Key` header (32 random bytes in base64url) and answers 201 for a new booking or 200 with the same `{ appointment }` for one that key already booked (see safe retries for the shop).
- `invalid_request` also covers 405 (wrong method, with an `Allow` header), 413 (body too large: 16 KB for JSON, 4 MB for photos) and 415 (a JSON body sent without `Content-Type: application/json`, or a photo that isn't `image/jpeg`). Requiring the JSON type means no other website can make its visitors' browsers book: a page can only send it cross-site after a CORS preflight, and the API answers none.
- `POST /api/owner/payments/:id/complete` answers 200 with the payment and Stripe's current `status`; the app should treat only `"succeeded"` as paid.
- `GET /api/owner/availability`: the same query and answer as `GET /api/availability`, with the owner key and without the lead time, so a walk-in can take the next slot that hasn't started yet.
- `GET /api/owner/me`: `stripe.locationId` is the Terminal location the owner app connects Tap to Pay to (`STRIPE_TERMINAL_LOCATION_ID`), `null` until Stripe is configured.
- `GET /api/catalog` (public, `Cache-Control: public, max-age=300`, no database) answers with `data/catalog.json` as the Kit exports it: the booking catalog (services, barbers, offerings with their price label and kind, hours, time zone, lead time, window, slot interval, `firstAvailable`) plus what the website shows: `shop` (name, phone in E.164 and for display, address and its lines, coordinates, Instagram, Apple Maps and Google Maps links, the review and website links, about, highlights, payment methods, accessibility), each service's `description`, `category` and `popular`, and each barber's `title`, `bio`, `specialties`, `monogram` and `instagram` (if any). The booking code ignores those extra fields.
- `GET /api/availability`: `from` defaults to today and must be within a year of it; `days` defaults to 1 (max 31). `serviceId` + `barberId=any` works for the services listed in the catalog's `firstAvailable` (those at least two barbers share); for the others it's a 400 and the app should ask for a barber.
- `GET /api/owner/appointments`, `/api/owner/time-off` and `/api/owner/payments` take shop-local days: `date`, or `from` and `to` (inclusive; at most 62 days, or 366 for time off), defaulting to today. Time off is listed when it overlaps those days.
- No-show protection adds, all additive (older apps keep working until the owner turns protection on, when they get `card_required` and need an update):
  - `Appointment.card`: `{ brand, last4 }` (Stripe's brand: `visa`, `mastercard`, `amex`, `discover`, …) or `null`; `Appointment.noShowFee`: `{ amountCents, fullPrice, status: "none"|"pending"|"charged"|"declined"|"needsAction", chargedAt, message, customerCancelledAt, lateCancelWindowMinutes, reason: "noShow"|"lateCancel"|null }` or `null` (no card on file). `fullPrice` is `true` when the agreed fee is the booked service's whole price (as at 100%). `Payment.kind`: `"inPerson"`, `"noShowFee"` or `"lateCancelFee"`.
  - `GET /api/no-show-policy?offeringId=…` (or `serviceId=…&barberId=any`) → `{ required, minFeeCents, maxFeeCents, policyText, lateCancelWindowMinutes, warning: { title, message } }` (all but `required` `null` when no card is needed; `lateCancelWindowMinutes` also `null` with late cancellations off).
  - `POST /api/cards/checkout` (`X-Card-Token`, body `{ offeringId }` or `{ serviceId, barberId: "any" }`) → 201 `{ url, sessionId }`; 400 when the booking needs no card; 429; 503 `stripe_not_configured`.
  - `GET /api/cards/return?session_id=…` → 302 to `izzyclipz://card-saved?session_id=…` (or `izzyclipz://card-failed`); `GET /api/cards/cancel` → 302 to `izzyclipz://card-cancelled`.
  - `POST /api/cards` (`X-Card-Token`, body `{ sessionId }`) → 201 `{ card: { brand, last4, expMonth, expYear } }`, or 200 with the same card when saved before; 400, 404, 429, 503 as above.
  - `POST /api/appointments`: optional `X-Card-Token` header and `noShowPolicy` and `keepCard` (boolean) body fields; new errors 400 `card_required` and 409 `policy_changed`.
  - `POST /api/owner/appointments/:id/no-show-fee` (a no-show or a late cancellation) → `{ appointment }` (see `noShowFee.status` and `reason`); 409 `not_chargeable`; 404; 503 `stripe_not_configured`.
  - `PATCH /api/owner/appointments/:id` with `status: "noShow"` on a booking with a card on file before its start → 409 `not_started`.
  - `POST /api/appointments/:id/cancel` inside the agreed late-cancellation window without `acceptLateCancelFee: true` → 409 `late_cancel_fee` (the message is the warning to show; nothing changes). Every app version that can book with a card must handle it, so ship that with the card screen.
  - `GET /api/owner/no-show-settings` → `{ noShowSettings: { enabled, feeMode: "percent"|"flat", percent, flatCents, lateCancelEnabled, lateCancelWindowMinutes } }` (to start: `false`, `"percent"`, `100`, `2000`, `true`, `60`); `PATCH` with any of those fields → the same (`percent` 1–100, `flatCents` 50–50,000, `lateCancelWindowMinutes` 30–2,880, all whole numbers). Unknown fields are a 400.
  - `X-Card-Token` is like a manage token: exactly 32 bytes in canonical base64url (43 characters), or a 400.
- `POST /api/owner/time-off` accepts `barberId` missing or `null` for the whole shop. Blocking time over existing appointments keeps them; it only stops new bookings.
- Stripe Connect and computers add, all additive:
  - `GET /api/owner/stripe` → `{ mode: "connect"|"direct"|"off", status, accountId, businessName, livemode, chargesEnabled, payoutsEnabled, detailsSubmitted, requirementsDue, message, dashboardUrl, checkedAt }`; `POST /api/owner/stripe/connect` `{ returnTo }` → 201 `{ url, expiresAt }`, or 409 `stripe_connect_off`; `DELETE /api/owner/stripe/connect` → the same JSON, `notConnected`.
  - `GET /api/stripe/connect/return?state=…` and `…/refresh?state=…`: browser pages (302, or a 400/429 HTML page).
  - `GET /api/owner/me` keeps `stripe` (in connect mode `configured` is true once the account can take card payments, and `locationId` is its Terminal location) and adds `connection: { mode, status, businessName }`, from the cache.
  - `POST /api/owner/computer-codes` → 201 `{ code, expiresAt, expiresInSeconds }`; `POST /api/computer-sessions` `{ code, name }` → 201 `{ token, session: { id, name, createdAt, lastUsedAt, expiresAt, current } }`; `GET /api/owner/computer-sessions` → `{ sessions }`; `DELETE …/:id`, `DELETE …` and `DELETE …/current` → 204.
  - `POST /api/cards/checkout` takes `returnTo: "web"`: Stripe Checkout then comes back through `/api/cards/return?…&to=web` and `/api/cards/cancel?to=web`, which redirect to `<PUBLIC_BASE_URL>/book/card-return?status=saved&session_id=…`, `?status=cancelled` or `?status=failed`. The app's links are unchanged.
  - New errors: 409 `stripe_connect_off`, 400 `wrong_code`, 403 `forbidden`.

## Sales and analytics

The shop rings up each client at checkout, in the Business app or on the website's Business area, and the analytics are built from those sales. Every definition is in `src/analytics.ts`, and in plain words for the owner in `docs/analytics.md`.

- **A sale** gives credit to one barber, may check out one appointment, is paid `card` (Tap to Pay, through Stripe), `cash` or `other` (Zelle, Cash App, Squire…: recorded only), and has 1 to 20 items: a catalog `service`, one of the shop's `product`s (hidden ones too) or a `custom` item with a name and a price (a gift card). Quantities are 1 to 99 (1 by default), prices $0 to $10,000, and so is the total. Names and prices are copied onto each item when it's sold, so renaming, repricing or deleting a product later never changes a sale (a deleted product's items keep its name, with `productId: null`).
- **Prices** default to the appointment's booked price for the appointment's own service, otherwise to the barber's menu price for the service (the price must be entered when the barber doesn't offer it, or has more than one price for it, like Flowxbori's two haircuts), and to the product's price (the price must be entered when the product has none).
- **Checking out an appointment**: it must be booked or completed (409 `not_checkoutable` for a cancelled or no-show one) and not checked out already (409 `already_checked_out`; one live sale per appointment, kept by a unique index). In the same transaction it becomes completed and paid with the sale's total, unless succeeded card payments already paid it (then the card's numbers stay). The barber and the client's name default to the appointment's. A checked-out appointment stays completed: reopening, cancelling or marking it a no-show is a 409 `already_checked_out` until its sale is voided.
- **Card sales**: `POST /api/owner/payments` takes the same ticket as `sale` (without `method`). It's checked like a cash sale, the amount must be its total (400 `amount_mismatch`), and a top-level `appointmentId` must be the ticket's (it stands for it when the ticket names none). The ticket is kept in `payments.sale_draft`, and when the payment succeeds (`…/complete` or the webhook, whichever comes first, in the transaction that marks it succeeded, with the payment row locked) it's recorded once, as a `card` sale sold when Stripe says the card went through (`payments.succeeded_at`: the charge's time, or the webhook event's), so a webhook Stripe sends again late, or an app that confirms the next morning, still puts it on the right day. If the appointment was checked out, cancelled or marked a no-show meanwhile, the sale is recorded without it, so the money still counts, the payment lets go of the appointment too (so it doesn't change what the appointment shows as paid), and that's logged. A payment without `sale` works as before and records no sale.
- **Voiding** (`POST /api/owner/sales/:id/void`) is idempotent and keeps an optional reason. A voided sale no longer counts anywhere, and its appointment (still completed) can be checked out again; a cash or other sale's appointment is unpaid again, unless a card paid it. If a card sale for that appointment had to be recorded without it (the appointment was checked out another way while the card went through), it takes the appointment back: it becomes its checkout and the card marks it paid, so the visit counts once, and the answer's `message` says so. **Voiding a card sale doesn't refund the card**: refunds are made in the Stripe Dashboard, and the answer's `message` says so.
- **Analytics** (`GET /api/owner/analytics`) read everything in one read-only snapshot with nine indexed queries (range scans on `sales.sold_at`, `appointments.start_at`, the fees' `payments.succeeded_at` and the time-off index), adding up by shop-local day or month with day boundaries worked out by the server in the shop's time zone. Nothing calls Stripe, so the page can poll every 30 seconds.

Contract (owner routes, all additive; a computer signed in with a code may use every one of them, but card sales start on the iPhone, since `POST /api/owner/payments` takes only the owner key):

- `POST /api/owner/sales` with `{ barberId?, appointmentId?, customerName?, method: "cash"|"other", items: [{ kind: "service", serviceId, unitCents?, quantity? } | { kind: "product", productId, unitCents?, quantity? } | { kind: "custom", name, unitCents, quantity? }] }` → 201 `{ sale }`; an optional `Idempotency-Key` (32 random bytes in base64url) works like shop bookings: the same request again gets 200 with the same `{ sale }` as it is now, the same key for another sale is a 400. `method: "card"` is a 400 that says to use Tap to Pay.
- `Sale`: `{ id, barberId, barberName, appointmentId, customerName, method, paymentIntentId, totalCents, items: [{ kind, serviceId, productId, name, quantity, unitCents, totalCents }], soldAt, voidedAt, voidReason }`.
- `GET /api/owner/sales?date=YYYY-MM-DD` (default today) → `{ date, sales (newest first, voided ones too), totals: { totalCents, count } }`; the totals leave voided sales out.
- `POST /api/owner/sales/:id/void` with `{ reason? }` (or no body at all) → `{ sale, message }`.
- `POST /api/owner/payments`: optional `sale` (above); 400 `amount_mismatch`. `Payment.saleId`: the card sale its success recorded (voided or not), or `null`.
- Owner appointments gain `sale: { id, totalCents, method } | null`, the live sale, and `completedAt` (when it was first marked completed or checked out, never cleared: a booking with a card on file that was completed can't become a no-show, even after it's reopened, so the website and the apps can tell before trying); the client's own view of an appointment has neither.
- `GET /api/owner/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD[&barberId=…]` (inclusive shop-local days, both defaulting to today, at most 366 days, within 10 years of today) → `{ from, to, barberId, timeZone, generatedAt, granularity, totals, previous, productivity, topBarber, leaderboard, services, products, series, barbers }`, `Cache-Control: no-store` (see `docs/analytics.md` and `test/fixtures/contract/analytics.json`). An unknown barber is a 400.
- New errors: 409 `not_checkoutable`, 409 `already_checked_out`, 400 `amount_mismatch`.
