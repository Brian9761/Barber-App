# Izzy Clipz API

The small server behind the Izzy Clipz app and the Izzy Clipz Business owner app: live booking with each barber's calendar, the owner's schedule, time off and walk-ins, the shop's own products (photos in Vercel Blob), Google and Yelp reviews, in-person card payments with Stripe Terminal (Tap to Pay on iPhone), and no-show protection (a card saved with Stripe Checkout when booking online, charged only if the client doesn't come or cancels less than an hour before, and only when the owner decides to).

TypeScript on Vercel Functions (Node 24), Postgres on Neon, region `pdx1`. One function (`api/index.ts`) serves every route through a small router, so the Hobby plan's 12-function limit never matters.

Node 22.12 or later (`.nvmrc` says 24, which is what Vercel runs).

```sh
cd server
npm ci
npm test              # vitest: everything, against PGlite (no database to install)
npx tsc --noEmit      # strict type check (also what `npm run build` does on Vercel)
```

```sh
DATABASE_URL=postgres://… OWNER_KEY=… npm run migrate   # once
DATABASE_URL=postgres://… OWNER_KEY=… npm run dev       # http://localhost:3000/api/health
```

`npm run dev` (`scripts/dev.ts`) serves the same app with the production dependencies over plain Node HTTP and reads `.env.local` if it exists, so it needs no Vercel login. `vercel dev` works too once the project is linked.

To run the same tests against a **real Postgres** (true concurrency, pool of 5), point `TEST_DATABASE_URL` at a role that can create databases. Each test file gets its own throwaway database:

TEST_DATABASE_URL=postgres://postgres@127.0.0.1:5432/postgres npm test

## Migrations

```sh
DATABASE_URL_UNPOOLED=postgres://… npm run migrate    # or with .env.local from `vercel env pull`
```

Applies `migrations/NNN_name.sql` in order, each in its own transaction, recorded with a checksum in `schema_migrations`. Running it again does nothing; two runs at once are serialized by an advisory lock. It refuses to continue if an applied file was edited: add a new numbered file instead. It then upserts the barbers from `data/catalog.json` (barbers no longer listed stay in the table, marked inactive, because old bookings point at them).

Run it once when the database is created, after every new migration, and after every catalog change. It isn't part of the Vercel build, so preview deployments can't change the production schema. That also means a new migration has to be applied **before** the code that needs it goes live: `002_manage_token_unique.sql` adds the `any_barber` column that every booking writes, `003_owner_idempotency_key.sql` the `idempotency_key_hash` column, and `004_no_show_protection.sql` the card and fee columns every booking writes, the `saved_cards` and `settings` tables and the payments' `kind` (with the late-cancellation window and the fee's reason), so a database without them can't take bookings or list payments. All four only add things, so the code already live keeps working on the new schema: migrate first, then deploy.

`006_sales.sql` adds the `sales` and `sale_items` tables, `payments.sale_draft` (a card checkout's ticket) and, on appointments, the live sale (`sale_id`, `sale_total_cents`, `sale_method`) that every owner view of an appointment reads, so it too must be applied before the code that needs it. It only adds things: rows from before it stay valid, and the code already live ignores the new columns.

## Deploy

1. **Project**: a Vercel project on this repo with **Root Directory = `server`** and framework **Other**. `vercel.json` sets the region (`pdx1`), the `/api/*` rewrite to the one function, its 30 s limit and the daily cron. `package.json` `engines` selects Node 24.
2. **Database**: add **Neon** from the Vercel Marketplace in region **`pdx1`** (it can't be changed later), with Neon Auth off, connected to Production, Preview and Development. Leave preview branching off at first. Then run `npm run migrate` with the new `DATABASE_URL_UNPOOLED`.
3. **Photos**: create a **public** Blob store in `pdx1` and connect it to the project.
4. **Secrets**: add `OWNER_KEY`, `CRON_SECRET` and, when ready, the Google, Yelp and Stripe variables above. Redeploy after changing variables.
5. **Stripe** (when the shop's account is connected): create a Terminal Location for the shop and set `STRIPE_TERMINAL_LOCATION_ID`. Add a webhook endpoint at `https://<domain>/api/stripe/webhook` with API version `2026-10-28.endive` (stripe-node 23's) for `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `payment_intent.processing` and `payment_intent.requires_action`, and set `STRIPE_WEBHOOK_SECRET` (the same events keep no-show fees right). For no-show protection, keep **Cards** turned on under Settings → Payment methods (Apple Pay comes with it on Stripe's page), and check the shop's public business details and statement descriptor in the Dashboard's settings, since that's what clients see on Stripe's card page and on their statement. No-show protection stays off until the owner turns it on in the Business app; do that only with a live key, and once the app versions with the card screen are in the App Store (older ones can't add a card, so their clients couldn't book online).
6. **Check**: `GET https://<domain>/api/health` → `{ "ok": true, "version": "4.0.0" }`, then `npm run smoke -- https://<domain>`. Point the apps at the production domain, not at a per-deployment URL (those are behind Deployment Protection).

Vercel's Hobby plan is for non-commercial use only; a shop taking bookings and payments needs Pro. Pro also allows an hourly cron (see the Yelp note below).

## How it behaves

- **Times**: the API speaks UTC instants (`2026-11-02T18:00:00Z`, no fractional seconds) and shop-local days (`2026-11-02`). All day and hour math happens in the catalog's time zone (`America/Los_Angeles`) with Luxon, never in the server's own zone, so daylight saving changes are handled by tzdata.
- **Availability** follows the Kit's `BookingCalendar`: start times every 30 minutes from opening, ending by closing, at least 30 minutes from now, today through today + 60 days, minus the barber's booked or completed appointments and time off (theirs or the whole shop's). Every requested day is listed, with no slots when there's nothing to book. "Any barber" uses the catalog's `firstAvailable` offerings: a start is open when one of those barbers is free for their own item's length, and `barberIds` lists the free ones in team order.
- **Booking** is one transaction with no global lock: the barber rows are share-locked (time off takes them exclusively, so a booking and new time off can't interleave), time off is checked, and the exclusion constraint `appointments_no_overlap` rejects overlaps (`23P01` → 409 `slot_taken`). "Any barber" picks the free barber with the fewest live bookings that day, ties in team order, and moves to the next one if the constraint says it was just taken. Customers must pick one of the calendar's start times. The shop may book any minute inside opening hours, including "now" or earlier today, with no lead time; seconds are dropped.
- **Limits**: 5 booking attempts per IP per hour (counted in 10-minute buckets of a sliding hour, after the request passes validation; a retry of a booking that went through isn't an attempt; the IP is stored only as a hash), and 3 upcoming booked appointments per phone number (shop bookings count too). Both answer 429 `rate_limited`, with a message that says which limit it was and what helps (the apps show it as is: "Try again in an hour" for the IP limit, "Cancel one" for the phone limit). The shop's own bookings have no IP limit. Consider one Vercel WAF rate-limit rule on `/api/*` as an outer guard.
- **Manage tokens**: 32 random bytes, base64url (43 characters), returned once at booking. The app may make its own and send it as `X-Manage-Token` on `POST /api/appointments` (see safe retries); otherwise the server makes one. Only the SHA-256 is stored (unique per appointment) and it's compared in constant time. A missing `X-Manage-Token` is 401; a wrong token or unknown id is 404, so ids can't be probed. Customers can cancel until the appointment starts.
- **Safe retries**: the app's own manage token doubles as the booking's idempotency key, so a retry after a lost answer (a flaky mobile network) can't book twice or get `slot_taken` for the client's own appointment. If an appointment already has that token and the request asks for the same target in the same way (the same `offeringId`, or the same `serviceId` with `barberId: "any"`), the same start and the same phone number, the answer is 200 with `{ appointment, manageToken }` (the same token, the appointment as it is now, even if it has been cancelled since); the name, email and note aren't compared. The same token with other details is 400 `invalid_request` ("That booking token was already used."). A token that isn't exactly 32 bytes in canonical base64url is 400 too. Retries are answered before the time rules and the IP limit, so they work after the lead time has passed and once the hour's attempts are used up. Two copies of one request racing make one appointment: the unique index on `manage_token_hash` (or the barber's overlap constraint) stops the second insert, and it answers like a retry. Shop bookings ignore the header and use `Idempotency-Key` instead (below).
- **Safe retries for the shop**: the owner app sends an `Idempotency-Key` (32 random bytes in base64url, like a manage token) with each walk-in or phone booking, and the same one when the owner books it again after a lost answer. If an appointment the shop booked already has that key, for the same target asked the same way, the same start (to the minute), the same client name and the same phone number (or none), the answer is 200 with `{ appointment }` as it is now; the email and note aren't compared. The same key with other details is 400 `invalid_request` ("That booking key was already used for another booking."), and a malformed key is 400 too. Only the SHA-256 is stored (`idempotency_key_hash`, unique), and racing copies make one appointment, as above. Without the header, a repeated walk-in is booked again (for "any barber", in the next free chair).
- **Owner auth**: `Authorization: Bearer <OWNER_KEY>`, compared as SHA-256 digests in constant time.
- **Reviews**: Google is fetched live on every `GET /api/reviews` (field mask `rating,userRatingCount,reviews,googleMapsUri`) and passed through in Google's order; nothing from Google is stored, only our own daily call counter in `api_usage`. Over the daily limit, unconfigured or failing, Google comes back `available: false` with the Maps link; after a failure the server waits a minute before calling Google again (10 minutes for Yelp, serving its cached copy meanwhile), so a slow or broken API doesn't hold up every visitor. Yelp (only with a key) is cached in `yelp_cache`, refreshed when it's 12 hours old, served stale only while it's under 24 hours old (if Yelp is down), and deleted at 24 hours on every read. The daily cron also purges the whole Yelp cache, because a once-a-day job that runs up to an hour late can't otherwise bound how long an unread row sits; on Pro, change the cron to hourly to tighten that. Every response is `Cache-Control: no-store`.
- **Payments**: the server creates every PaymentIntent (`allowed_payment_method_types: ['card_present']`, `capture_method: 'automatic'`, USD), so the app can't change the amount. `POST /api/owner/payments/:id/complete` asks Stripe for the PaymentIntent and records its status; only `succeeded` marks the appointment paid (the paid amount is the sum of its succeeded payments). The webhook does the same from Stripe's side, and a late event can't undo `succeeded` or `canceled`. Every Stripe error is logged (its type, code, param, status, request id and message, with keys and client secrets cut out). A Terminal location Stripe turns down when making a connection token (a test-mode `tml_…` with a live key, or a typo) answers 500 `server_error` naming `STRIPE_TERMINAL_LOCATION_ID`, and a key it turns down names `STRIPE_SECRET_KEY`; the owner app shows that message when Tap to Pay can't start. Only a payment Stripe doesn't have is a 404.
- **No-show protection** (card on file): see the section below.
- **Errors** always look like `{ "error": { "code": "slot_taken", "message": "Someone just booked that time. Pick another." } }`, with messages written for the person using the app. Unexpected failures are logged (no request bodies or personal data) and answer 500 `server_error`.

## No-show protection

The client's rules: when protection is on, every online booking needs a card, and nothing is charged at booking. Two cases can be charged, both the same fee, and **the owner decides each time** (nothing is charged automatically): a **no-show**, and a **late cancellation**, when the client cancels in the app less than 1 hour before the start. Cancelling earlier is free, and a cancellation by the shop is never charged. The fee starts at the full price of the booked service (100%). In the Business app the owner changes it (a percentage of the service, 1–100%, or a flat amount, $0.50–$500), turns late-cancellation charges off or changes their window (30 minutes to 48 hours), or turns protection off. **Protection is off until the owner turns it on**: setting `STRIPE_SECRET_KEY` alone (say a test key, to try Tap to Pay) never changes how clients book, since Stripe's test-mode card page turns real cards down.

- **When it applies**: Stripe is set up (`STRIPE_SECRET_KEY`), the owner has turned it on, and the booked item has a fee of at least 50¢ (Stripe's smallest charge). Items included with a cut have none. Otherwise no card is asked for and booking works exactly as before. The shop's own bookings (walk-ins, phone) never need a card.
- **The fee rule** is in one place (`src/noshow.ts`): percent mode is `round(price × percent / 100)`, half up to the cent ("starting at" prices use the starting price); flat mode is the flat amount. The fee is worked out at booking, for the barber the booking lands with, and kept on the appointment, so changing the settings later never changes an existing booking's fee.
- **The policy and the warning**: `GET /api/no-show-policy` gives what the apps show. `policyText` is what the client agrees to, e.g. "No payment now. If you cancel less than 1 hour before your appointment, or don't come, Izzy Clipz may charge $40 (100% of the service) to this card. Cancelling in the app more than 1 hour before is free." (with late cancellations off: "If you don't come and haven't cancelled … Cancelling in the app before your appointment is free."). `warning` is the notice for the Pick a day and time step and Review: title "Full Service Cancellation & No-Show Fee" ("Late Cancellation & No-Show Fee" when the fee is less than the full price, "No-Show Fee" with late cancellations off) and message "Cancelling less than 1 hour before your appointment, or not showing up, is charged the full service price ($40). Cancelling in the app more than 1 hour before is free." `lateCancelWindowMinutes` is the window (`null` with late cancellations off). For "any barber" the amounts are the range of the barbers' fees ("$55–$60"). The app sends `policyText` back exactly with the booking (`noShowPolicy`); the server keeps it, the window it states and the consent time (the booking time) as the evidence for a dispute. If it's no longer the current policy for that booking (the owner just changed the fee or the window), the booking is a 409 `policy_changed` and the app shows the new policy.
- **Saving a card** uses Stripe Checkout in setup mode, so card numbers never reach the server or the apps. The app makes a card token (32 random bytes, base64url, like a manage token) and sends it as `X-Card-Token` to `POST /api/cards/checkout`; the server makes a Stripe Customer and a Checkout Session (`mode: setup`, cards only, the policy under the Save button, 60 minutes to finish) with the token's SHA-256 in its metadata, and answers with Stripe's URL. The app opens it in `ASWebAuthenticationSession` (callback scheme `izzyclipz`). Stripe returns to `GET /api/cards/return?session_id=…` (Checkout needs an https address), which redirects to `izzyclipz://card-saved?session_id=…`; Cancel on Stripe's page goes through `GET /api/cards/cancel` to `izzyclipz://card-cancelled` (and a return without a usable session id to `izzyclipz://card-failed`). The app then calls `POST /api/cards` with the session id and the same token: the server checks with Stripe that the session is one it made **for that token**, in setup mode and complete, and stores the card's brand, last 4 digits, expiry and Stripe ids under the token's SHA-256 (never the token). Saving again with the same token and session answers 200 with the same card, so a lost answer is safe; the same token for another session is a 400 (one token, one card); anyone who only knows the session id (it's in the return address) gets a 404, because they don't have the token. Both card endpoints allow 10 tries per network per hour (`rate_limited`), to blunt card testing.
- **Booking with the card**: `POST /api/appointments` with `X-Card-Token` and `noShowPolicy`. A missing or unknown card, a card that expires before the appointment's month, or a card saved in test mode once the shop uses a live key (or the other way round) is a 400 `card_required`, with a sentence saying which. These checks come before the booking-attempt limit, so they don't use up the network's attempts. A retry with the app's manage token (`X-Manage-Token`) is answered before any of this, as before: the card isn't part of "the same booking". One card can book any number of appointments.
- **Cancelling** in the app works as before at any time before the start; the server keeps when the client cancelled (`customer_cancelled_at`, never cleared). A request the status turns down (the shop had already marked the booking) still counts when it came before the start. The customer app warns before a cancellation inside the window ("may be charged $40").
- **Which booking can be charged** (`src/feecase.ts`, only the booking's own agreed terms count, never today's settings):
  - a **late cancellation**: the booking is cancelled by the client, who cancelled less than the agreed window before the start (exactly 1 hour before is still free), and the agreed policy had late cancellations in it. It can be charged right away. If the shop reopens it, it can't be charged any more.
  - a **no-show**: the booking is marked no-show, its start has passed, and the client never cancelled nor asked to. A booking with a card on file can't be marked a no-show before its start (409 `not_started`, "You can mark a no-show once the appointment has started."), so the client can still cancel.
  - anything else is a 409 `not_chargeable` that says why: "The client cancelled at least 1 hour before, so there's no fee.", "The client cancelled this booking in the app, so there's no fee.", "The shop cancelled this booking, so there's no fee.", "Mark the appointment as a no-show first.", "The appointment hasn't started yet, so it can't be a no-show.", "This booking has no card on file, so there's no fee to charge."
  - `appointment.noShowFee.reason` says which case it is: `"noShow"`, `"lateCancel"`, or `null` when neither applies (once the shop tried to charge it, what that charge was for).
- **Charging** (`POST /api/owner/appointments/:id/no-show-fee`, owner key, for either case): the server creates and confirms an off-session PaymentIntent (`off_session: true`, `confirm: true`, the Customer and card saved at booking, `allowed_payment_method_types: ['card']`, the stored fee in USD, description "No-show fee: …" or "Late cancellation fee: …", metadata `{ kind: "no_show_fee" | "late_cancel_fee", appointment_id, attempt }`) with the Stripe idempotency key `izzy-no-show-fee-<appointment id>-<attempt>`. While it decides, the appointment row is locked, so the fee is charged at most once: once it's `charged`, charging again answers the same appointment without calling Stripe. A try whose answer was lost (a timeout, an outage) leaves the fee `pending`; the next try first asks Stripe for that attempt's PaymentIntent (`paymentIntents.list` for the card's own Customer, created since the attempt began, matched by metadata), because Stripe may forget an idempotency key after 24 hours and a reused key would then charge again. Only if Stripe has none is the request sent again, with the same key. A `pending` fee Stripe is still processing is looked up again instead. Only a definite "no" from Stripe (`declined`, or `needsAction` when the bank wants the client to approve it, which an off-session charge can't do) lets the next try make a new PaymentIntent. Every answer is 200 with `{ appointment }`; `appointment.noShowFee.status` says what happened and `message` why, in plain words for the owner ("The card was declined: there isn't enough money on it."; never "lost" or "stolen"). Only a PaymentIntent Stripe reports as `succeeded` makes the fee `charged`.
- **Checking a fee** with `POST /api/owner/payments/:id/complete` (as for in-person payments) works too: it updates the fee from Stripe, and still never marks the appointment paid.
- **Payments**: every fee PaymentIntent is in `payments` with `kind: "noShowFee"` or `"lateCancelFee"`, so Payments today lists it as such (with Stripe's status), on the day Stripe made it. A fee is not a payment for the service: it never marks the appointment paid, and the paid amount only adds up in-person payments.
- **The webhook** keeps fees right for answers that come later: `payment_intent.succeeded` makes the fee charged (any fee PaymentIntent of that appointment, even an older attempt's, since money moved), failures and cancellations make the current attempt declined (or `needsAction` when Stripe's `last_payment_error` is `authentication_required`), a late "processing" can't undo a decline, and nothing undoes charged. A fee PaymentIntent the server never got to write down (it stopped right after Stripe charged) is found by its metadata and recorded.
- **Refunds and disputes**: reopening a charged appointment doesn't refund it; refunds are made in the Stripe Dashboard. The stored policy text (with its window) and consent time are the evidence if a client disputes a fee.
- **Privacy**: only the card's brand, last 4 digits, expiry and Stripe ids are stored. Saved cards stay as long as the client keeps the token (Remember me); expired cards are simply refused at booking.

**Costs** (Stripe, US): a no-show or late-cancellation fee is a card-not-present charge at Stripe's online rate, 2.9% + 30¢ (a $40 fee nets about $38.54). Saving a card costs nothing. A dispute costs $15, refunded if the shop wins it.

### Contract details worth knowing

- `POST /api/appointments` takes an optional `X-Manage-Token` header (the app's own manage token, 32 random bytes in base64url) and answers 201 for a new booking or 200 for a retry of one that went through (see safe retries above). Without it, nothing changes.
- `POST /api/owner/appointments` takes an optional `Idempotency-Key` header (32 random bytes in base64url) and answers 201 for a new booking or 200 with the same `{ appointment }` for one that key already booked (see safe retries for the shop).
- `invalid_request` also covers 405 (wrong method, with an `Allow` header), 413 (body too large: 16 KB for JSON, 4 MB for photos) and 415 (a JSON body sent without `Content-Type: application/json`, or a photo that isn't `image/jpeg`). Requiring the JSON type means no other website can make its visitors' browsers book: a page can only send it cross-site after a CORS preflight, and the API answers none.
- `POST /api/owner/payments/:id/complete` answers 200 with the payment and Stripe's current `status`; the app should treat only `"succeeded"` as paid.
- `GET /api/owner/availability`: the same query and answer as `GET /api/availability`, with the owner key and without the lead time, so a walk-in can take the next slot that hasn't started yet.
- `GET /api/owner/me`: `stripe.locationId` is the Terminal location the owner app connects Tap to Pay to (`STRIPE_TERMINAL_LOCATION_ID`), `null` until Stripe is configured.
- `GET /api/availability`: `from` defaults to today and must be within a year of it; `days` defaults to 1 (max 31). `serviceId` + `barberId=any` works for the services listed in the catalog's `firstAvailable` (those at least two barbers share); for the others it's a 400 and the app should ask for a barber.
- `GET /api/owner/appointments`, `/api/owner/time-off` and `/api/owner/payments` take shop-local days: `date`, or `from` and `to` (inclusive; at most 62 days, or 366 for time off), defaulting to today. Time off is listed when it overlaps those days.
- No-show protection adds, all additive (older apps keep working until the owner turns protection on, when they get `card_required` and need an update):
  - `Appointment.card`: `{ brand, last4 }` (Stripe's brand: `visa`, `mastercard`, `amex`, `discover`, …) or `null`; `Appointment.noShowFee`: `{ amountCents, status: "none"|"pending"|"charged"|"declined"|"needsAction", chargedAt, message, customerCancelledAt, lateCancelWindowMinutes, reason: "noShow"|"lateCancel"|null }` or `null` (no card on file). `Payment.kind`: `"inPerson"`, `"noShowFee"` or `"lateCancelFee"`.
  - `GET /api/no-show-policy?offeringId=…` (or `serviceId=…&barberId=any`) → `{ required, minFeeCents, maxFeeCents, policyText, lateCancelWindowMinutes, warning: { title, message } }` (all but `required` `null` when no card is needed; `lateCancelWindowMinutes` also `null` with late cancellations off).
  - `POST /api/cards/checkout` (`X-Card-Token`, body `{ offeringId }` or `{ serviceId, barberId: "any" }`) → 201 `{ url, sessionId }`; 400 when the booking needs no card; 429; 503 `stripe_not_configured`.
  - `GET /api/cards/return?session_id=…` → 302 to `izzyclipz://card-saved?session_id=…` (or `izzyclipz://card-failed`); `GET /api/cards/cancel` → 302 to `izzyclipz://card-cancelled`.
  - `POST /api/cards` (`X-Card-Token`, body `{ sessionId }`) → 201 `{ card: { brand, last4, expMonth, expYear } }`, or 200 with the same card when saved before; 400, 404, 429, 503 as above.
  - `POST /api/appointments`: optional `X-Card-Token` header and `noShowPolicy` body field; new errors 400 `card_required` and 409 `policy_changed`.
  - `POST /api/owner/appointments/:id/no-show-fee` (a no-show or a late cancellation) → `{ appointment }` (see `noShowFee.status` and `reason`); 409 `not_chargeable`; 404; 503 `stripe_not_configured`.
  - `PATCH /api/owner/appointments/:id` with `status: "noShow"` on a booking with a card on file before its start → 409 `not_started`.
  - `GET /api/owner/no-show-settings` → `{ noShowSettings: { enabled, feeMode: "percent"|"flat", percent, flatCents, lateCancelEnabled, lateCancelWindowMinutes } }` (to start: `false`, `"percent"`, `100`, `2000`, `true`, `60`); `PATCH` with any of those fields → the same (`percent` 1–100, `flatCents` 50–50,000, `lateCancelWindowMinutes` 30–2,880, all whole numbers). Unknown fields are a 400.
  - `X-Card-Token` is like a manage token: exactly 32 bytes in canonical base64url (43 characters), or a 400.
- `POST /api/owner/time-off` accepts `barberId` missing or `null` for the whole shop. Blocking time over existing appointments keeps them; it only stops new bookings.

## Sales and analytics

The shop rings up each client at checkout, in the Business app or on the website's Business area, and the analytics are built from those sales. Every definition is in `src/analytics.ts`, and in plain words for the owner in `docs/analytics.md`.

- **A sale** gives credit to one barber, may check out one appointment, is paid `card` (Tap to Pay, through Stripe), `cash` or `other` (Zelle, Cash App, Squire…: recorded only), and has 1 to 20 items: a catalog `service`, one of the shop's `product`s (hidden ones too) or a `custom` item with a name and a price (a gift card). Quantities are 1 to 99 (1 by default), prices $0 to $10,000, and so is the total. Names and prices are copied onto each item when it's sold, so renaming, repricing or deleting a product later never changes a sale (a deleted product's items keep its name, with `productId: null`).
- **Prices** default to the appointment's booked price for the appointment's own service, otherwise to the barber's menu price for the service (the price must be entered when the barber doesn't offer it, or has more than one price for it, like Flowxbori's two haircuts), and to the product's price (the price must be entered when the product has none).
- **Checking out an appointment**: it must be booked or completed (409 `not_checkoutable` for a cancelled or no-show one) and not checked out already (409 `already_checked_out`; one live sale per appointment, kept by a unique index). In the same transaction it becomes completed and paid with the sale's total, unless succeeded card payments already paid it (then the card's numbers stay). The barber and the client's name default to the appointment's. A checked-out appointment stays completed: reopening, cancelling or marking it a no-show is a 409 `already_checked_out` until its sale is voided.
- **Card sales**: `POST /api/owner/payments` takes the same ticket as `sale` (without `method`). It's checked like a cash sale, the amount must be its total (400 `amount_mismatch`), and a top-level `appointmentId` must be the ticket's (it stands for it when the ticket names none). The ticket is kept in `payments.sale_draft`, and when the payment succeeds (`…/complete` or the webhook, whichever comes first, in the transaction that marks it succeeded, with the payment row locked) it's recorded once, as a `card` sale sold at that moment. If the appointment was checked out, cancelled or marked a no-show meanwhile, the sale is recorded without it, so the money still counts, the payment lets go of the appointment too (so it doesn't change what the appointment shows as paid), and that's logged. A payment without `sale` works as before and records no sale.
- **Voiding** (`POST /api/owner/sales/:id/void`) is idempotent and keeps an optional reason. A voided sale no longer counts anywhere, and its appointment (still completed) can be checked out again; a cash or other sale's appointment is unpaid again, unless a card paid it. **Voiding a card sale doesn't refund the card**: refunds are made in the Stripe Dashboard, and the answer's `message` says so.
- **Analytics** (`GET /api/owner/analytics`) read everything in one read-only snapshot with nine indexed queries (range scans on `sales.sold_at`, `appointments.start_at`, `payments.created_at` and the time-off index), adding up by shop-local day or month with day boundaries worked out by the server in the shop's time zone. Nothing calls Stripe, so the page can poll every 30 seconds.

Contract (owner routes; all additive):

- `POST /api/owner/sales` with `{ barberId?, appointmentId?, customerName?, method: "cash"|"other", items: [{ kind: "service", serviceId, unitCents?, quantity? } | { kind: "product", productId, unitCents?, quantity? } | { kind: "custom", name, unitCents, quantity? }] }` → 201 `{ sale }`; an optional `Idempotency-Key` (32 random bytes in base64url) works like shop bookings: the same request again gets 200 with the same `{ sale }` as it is now, the same key for another sale is a 400. `method: "card"` is a 400 that says to use Tap to Pay.
- `Sale`: `{ id, barberId, barberName, appointmentId, customerName, method, paymentIntentId, totalCents, items: [{ kind, serviceId, productId, name, quantity, unitCents, totalCents }], soldAt, voidedAt, voidReason }`.
- `GET /api/owner/sales?date=YYYY-MM-DD` (default today) → `{ date, sales (newest first, voided ones too), totals: { totalCents, count } }`; the totals leave voided sales out.
- `POST /api/owner/sales/:id/void` with `{ reason? }` (a JSON body; `{}` for no reason) → `{ sale, message }`.
- `POST /api/owner/payments`: optional `sale` (above); 400 `amount_mismatch`. `Payment.saleId`: the card sale its success recorded (voided or not), or `null`.
- Owner appointments gain `sale: { id, totalCents, method } | null`, the live sale; the client's own view of an appointment doesn't have it.
- `GET /api/owner/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD[&barberId=…]` (inclusive shop-local days, both defaulting to today, at most 366 days, within 10 years of today) → `{ from, to, barberId, timeZone, generatedAt, granularity, totals, previous, productivity, topBarber, leaderboard, services, products, series, barbers }`, `Cache-Control: no-store` (see `docs/analytics.md` and `test/fixtures/contract/analytics.json`). An unknown barber is a 400.
- New errors: 409 `not_checkoutable`, 409 `already_checked_out`, 400 `amount_mismatch`.
