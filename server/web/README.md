# Izzy Clipz website

The shop's website: Home, Services, Barbers, Reviews, Visit, booking in five steps, My appointments, Get the app, the shop's four legal documents (see [The legal pages](#the-legal-pages)), and Izzy Clipz Business (`/business`), the owner's own area: the day's schedule and checkout, analytics, products and settings, signed in with a code from the iPhone app (see [Izzy Clipz Business](#izzy-clipz-business)). It's built into `../public` and served by the same Vercel project as the API, so it calls `/api/…` on its own origin and needs no settings. Vite 6, React 18.3, TypeScript (strict), React Router 6; every version is pinned in `package-lock.json`.

It's also a web app anyone can install: on an iPhone with Safari's Share → Add to Home Screen, on Android with Chrome's Install, on a computer with Chrome's or Edge's install button. It then opens full screen with the shop's icon, and works offline as far as it can (see [The web app](#the-web-app)). Izzy Clipz Business installs the same way as an app of its own. A demo version books, and runs Izzy Clipz Business on a sample shop, in the browser without the shop's server, so it can be published on its own (see [The demo version](#the-demo-version)).

## Commands

Run them here, in `server/web` (Node 22.13 or later).

| Command | What it does |
|---|---|
| `npm ci` | Installs the exact packages in `package-lock.json`. |
| `npm run dev` | The site on http://localhost:5173 with live reload. `/api` goes to the API's own dev server on http://localhost:3000, so start that first (`npm run dev` in `server/`). |
| `npm run dev:demo` | The demo version with live reload: no API needed. |
| `npm run build` | Type-checks and builds into `../public` (what Vercel serves), service worker included. The legal pages are drafts, unless the build is strict (`LEGAL_STRICT=1`, or `VERCEL_ENV=production`), which stops while any placeholder is left in `docs/legal` (see [The legal pages](#the-legal-pages)). |
| `npm run build:demo` | Type-checks and builds the demo version into `dist-demo/`, with its own `vercel.json`. |
| `DEMO_MOVED_TO=https://… npm run build:retired` | What takes the demo's place at its address once the real site is live somewhere else, into `dist-retired/` (see [Publishing the demo, and its way out](#publishing-the-demo-and-its-way-out)). |
| `npm test` | Unit tests (Vitest, Testing Library, jsdom) against the server's contract fixtures, and the build's own tools' tests (in Node). |
| `npm run typecheck` | The site's code, the service worker, and the build, test and end-to-end files. |
| `npm run serve:local` | The built site and the real API on an in-memory PGlite at http://127.0.0.1:4173, a fresh empty database every start. Needs `npm ci` in `server/` too. Good for trying the whole thing on a computer. |
| `npm run serve:demo` | The built demo at http://127.0.0.1:4174, hosted the way its `vercel.json` says. |
| `npm run e2e` | Playwright end-to-end tests in Chromium against the site and the real API (build first). |
| `npm run e2e:demo` | The same for the demo version (`npm run build:demo` first). |

## How it's put together

- `src/pages/`: one file per page. `src/booking/`: the five steps (`flow.ts` is the booking's state machine), the confirmation and the way back from Stripe's card page. `src/legal/`: the legal pages (a small Markdown reader, the page, and the placeholders' rules, which the build's `tools/legal.ts` shares).
- `src/api/`: the API client and the JSON types, field for field as the server writes them. Pages call `api` from `client.ts`; `http.ts` is the client over the network (every failure becomes an `ApiError` from `errors.ts`, with a plain sentence), and `backend.ts` says which one the site uses: the demo build swaps it for `src/demo/backend.ts`.
- `src/pwa/`: the web app's pieces: registering the service worker and the "A new version is ready · Reload" bar, the offline notice, the browser's install offer, the device and browser, opened as the app or not, the Add to Home Screen bar, the drawings on Get the app and its QR code. `src/sw/`: the service worker itself (`sw.ts`) and its rules (`routes.ts`).
- `src/business/`: Izzy Clipz Business (see [Izzy Clipz Business](#izzy-clipz-business)), loaded only when a `/business` page is opened. `business/index.html` is its page, with its own manifest and icons (`public/business/`).
- `src/demo/`: the demo version's stand-in for the shop (`api.ts`), its sample reviews and its notice; `src/demo/owner/` is the stand-in for the owner's API, with the sample shop's history and its analytics.
- `tools/`: the build's own helpers, run in Node: the service worker's list of files (`precache.ts`) and the retired demo (`retired.ts`); and `analytics-parity.test.ts`, which checks the demo's analytics against the server's own code.
- `src/lib/`: the rules the pages share, each with unit tests: tokens (32 random bytes in base64url, like the apps), US phone numbers, prices and lengths (like the Kit), the shop's clock and calendar (always the shop's time zone, whatever the visitor's computer says), the late-cancellation warning, `.ics` files and what the browser keeps.
- `src/styles/`: the design tokens (`tokens.css`: the apps' colors, the type scale, spacing and radii) and the shared pieces. The font is the apps' own: the system font first (SF Pro on Apple devices), then Inter, self-hosted from `@fontsource-variable/inter` and only downloaded where SF Pro isn't there. Nothing loads from another site.
- `src/assets/images/`: the app's photos (`IzzyClipz/Resources/Assets.xcassets`) as WebP.
- `src/assets/logo.ts`: the shop's logo as a vector, the same tracing the apps' logo images are drawn from. `src/components/Logo.tsx` draws it in the text color, so it's sharp at any size: white on the black bands (the nav, the hero, the sticker on the storefront photo) and near-black on the white and light gray ones (the footer, the Visit tile, Business). Only the nav's logo has a name for screen readers, "Izzy Clipz", as the link to Home; the others are decoration.
- `public/`: the icons made from the logo on black, rendered from the shop's vector logo (32 and 48 px for browser tabs, 180 px for iPhone home screens, 192 and 512 px in `manifest.webmanifest`, and a 512 px one with room around the logo for Android to crop to a circle or rounded square), the manifest, the offline page (`offline.html`), the share image link previews show (`og-image.png`, the logo on black, 1200×630) and `robots.txt`.

The site never moves on its own: no carousels, no autoplay, no animated page changes, and none at all when the system asks for reduced motion. Text is at least 17px, everything you can tap at least 44px, and every page has the phone number.

## The legal pages

`/privacy`, `/terms`, `/cancellation-policy` and `/accessibility` are the shop's Privacy Policy, Terms of Service, Cancellation & No-Show Policy and Accessibility Statement, drawn from `docs/legal/*.md` at the root of the repository (imported with `?raw`, in the pages' own script). `src/legal/markdown.ts` reads exactly the Markdown they use (headings, with ids as GitHub makes them, paragraphs, bold, links, nested bulleted lists, tables, block quotes, code and the trailing-backslash line break) into a tree that `LegalPage.tsx` draws as React elements: nothing from the files reaches the page as HTML. Links between the documents (`privacy.md#…`) open their pages here; other links stay as they are; the shop's number calls it and an email address writes to it. Each page has its title as its one main heading, its dates, "On this page" with its sections (open on a computer, a tap away on a phone), about 70 characters to a line, tables that fit a phone, and print styles without the nav and footer. They open offline like the other pages (`src/sw/routes.ts`).

- **Drafts until the shop publishes them.** Every build is a draft except a strict one: a draft starts with "Draft: not in effect yet. The shop will publish this when online booking opens." (in the demo, also that it's the demo), its "Effective date" and "Last updated" read "Not in effect yet", and each `[TO FILL IN: …]` shows as a highlighted "To be added by the shop: …", without anything pointing to the owner's checklist.
- **Strict** is `LEGAL_STRICT=1`, or `VERCEL_ENV=production` for a build that isn't the demo (`tools/legal.ts`). It shows no draft note, and the build stops while any of the four documents still has `[TO FILL IN`, naming each file and line. So the shop's site can't go to production with the documents unfinished; fill them in (`docs/legal/OWNER-CHECKLIST.md`) first.
- **Links to them:** every page's footer (Privacy Policy first, then Terms of Service, Cancellation & No-Show Policy and Accessibility), every Izzy Clipz Business page (small, in a new tab), Get the app and the offline page (the Privacy Policy). Booking says, right above "Book appointment", "By booking, you agree to our Terms of Service and Cancellation & No-Show Policy."; the fee notice ends with "Read the Cancellation & No-Show Policy"; and Your details says "Your details go to Izzy Clipz Barbershop and the services that run its booking, as our Privacy Policy explains." Those open in a new tab (screen readers hear so), so the booking stays where it is.

## The web app

- **Installable.** `public/manifest.webmanifest` names it Izzy Clipz, opens it full screen from `/?source=app` with the whole site in scope, black, with the icons above; `index.html` has the iPhone's tags (`apple-touch-icon`, `apple-mobile-web-app-capable` and `mobile-web-app-capable`, a black status bar, the title). That's all Chrome, Edge and Android need to offer to install it (a name, the 192 and 512 icons, a start page, a display mode); iPhones take any site to the Home Screen and open it as an app with these tags. Opened from the Home Screen the page reaches the screen's edges (`viewport-fit=cover`), and the nav, the menu, the footer and the page's sides keep clear of the notch, the status bar and the home bar (`env(safe-area-inset-*)`, in `tokens.css`).
- **The service worker** (`src/sw/`, built into `/sw.js` at the end of every build with the list of the build's files). It keeps this version's page, scripts, styles, Inter's Latin fonts, the shop's photos, the icons, the manifest and the offline page, each page with the headers it came with: so a page's revision is a hash of what's in it and of the hosting settings (`../vercel.json`, or the demo's `vercel.json` in this folder), and a change to the headers alone makes a new version too (`tools/precache.ts`). The site's pages open from that copy, also offline. A page this version doesn't know is asked for on the network, and without a connection `offline.html` answers: "You're offline. To book, call the shop: (442) 341-3053", with a tap-to-call link. From the API it keeps only the shop's public catalog (`/api/catalog`: menu, team and hours), network first and the last copy offline, so the app opens with them. Nothing with a token or personal data is ever kept: appointments, cards and the owner's area always go to the network, as do the reviews (Google's terms) and the open times. The demo's worker never asks `/api` at all.
- **New versions** install quietly next to the one in use and wait. The page shows "A new version is ready · Reload", and only a tap on Reload makes the new one take over and reloads the page; an app left open looks for one whenever it comes back on screen. `/sw.js` is served with `Cache-Control: no-cache` (`../vercel.json`).
- **Offline**, a line under the nav says how to book by phone, and My appointments shows nothing it can't check with the shop (it could have changed): it says so, and checks again once the connection is back.
- **Get the app** (`/app`, in the nav and the footer) opens on the visitor's own device, from what the browser says it is, with the others one tap away: on an iPhone, Safari's Share, Add to Home Screen and Add (and what to do inside Instagram or in another browser); on Android, an Install button with the browser's own question when Chrome offers one (`beforeinstallprompt`), and Chrome's menu otherwise; on a computer, Chrome's or Edge's install button or the steps, Add to Dock for Safari on a Mac, and Add tab to taskbar for Firefox on Windows (Firefox 143 and later). Each step has a drawing of what to tap in the site's style. On a computer, a QR code (made in the browser with `uqr`, from the address the site is open at) opens it on a phone. Opened as the app, it just says "You're using the app".
- **On phones**, "Add Izzy Clipz to your Home Screen · How" shows under the nav after the first booking or from the second visit, never in the app, and stays closed once closed, or once Chrome says the app is installed (`appinstalled`, or a yes to the Install button).
- **Carried into the app.** An app added to an iPhone's or iPad's Home Screen (iOS 17.2 and later), or to the Dock from Safari on a Mac, gets website data of its own: only the cookies are copied into it from Safari, not `localStorage`. So each appointment booked here is also kept, as its id and manage token only, in a first-party cookie (`izzy_appointments`, `SameSite=Strict`, refreshed whenever the site opens), and My appointments in the app brings in the ones it doesn't have yet, checked with the shop. The server never reads it. Older iPhones copy nothing; there the app's My appointments starts empty, and the appointments are still in Safari's. "Remember me" isn't carried: the client types their name once in the app.
- **Words for the device.** "Remember me on this phone", "No appointments booked on this computer yet": the site says phone, iPad, tablet or computer, from what the browser says it is, and on a computer Get the app says "with your other apps" where a phone has a Home Screen.
- **Opened as the app** (`display-mode: standalone`, or Safari's `navigator.standalone`; the page gets the `is-standalone` class), there's no browser around it, so the nav has a Back button on every page but Home and the booking steps, "Get the app" leaves the nav and the footer, and links to other sites (maps, Instagram, reviews) open outside the app. Calls work as they are.

## Izzy Clipz Business

The shop owner's area, on a computer (or a phone or tablet), for the same shop the iPhone app runs: `/business` is sign-in, then Today, Analytics, Products and Settings, in a local nav under the site's black bar with its red "Business" tag. It's the iPhone app's rules on a bigger screen, in the site's style and words, and every page works with the keyboard alone.

- **Signing in.** On the iPhone, Settings → Use on a computer shows a 6-digit code; typed here ("483 920" is fine), it becomes a session for this computer (`POST /api/computer-sessions`), named after the browser ("Chrome on Mac"), for 30 days. Only the session's token is kept, and the barber picked last for Sold by (see [What the browser keeps](#what-the-browser-keeps)); every call sends the token as `Authorization: Bearer …`. "Use the owner key instead" takes the owner key, which only makes a code (`POST /api/owner/computer-codes`) for a session the same way: the key itself is never kept. When the server turns the session down (signed out from the iPhone, or its 30 days are up), or the 30 days ran out while the page was closed, the page goes back to sign-in, saying why; Sign out (it asks first) ends the session on the server too. Other tabs follow along.
- **Today**: the day's appointments, a column per barber on a computer and one list in time order on a phone, with each one's status, what was paid and the card on file or its fee; time off, with its days and times when it runs into other days, as the app shows it ("Mon, Nov 2 at 6:50 PM – Fri, Nov 6 at 6:50 PM"); the day's sales below with their total; a day before or after, or any date. It refreshes every minute while it's on screen. An appointment opens in a side panel: call the client, Check out, Mark done, No-show (with a card on file once it has ended, otherwise once it has started; the panel says when), Cancel or Reopen (asking first), and charge the agreed no-show or late-cancellation fee to the card on file, asking first and naming the card. The fee follows the server's rules, in its words (`src/business/lib/fees.ts`, checked against `test/fixtures/fee-cases.json`): a no-show only once the appointment has ended; a completed visit never becomes a no-show (Reopen says so first, and only the server knows a visit was completed before it was reopened, so its `already_completed` answer shows as it says); a cancellation within 15 minutes of booking is never late; and nothing is charged more than 7 days after the appointment: until then the panel says until when it can be charged, and after that Charge isn't offered and a plain line says why (a try whose answer never came can still be checked). What happened takes the focus where the button was, so it's read out and Tab goes on to what can be done now ("Marked done.", the fee charged); a fee that couldn't be charged says why next to its button, with Go to Settings when Stripe isn't connected. A declined card or one waiting on the client says what to do.
- **Checkout** (an appointment's, or New sale for a walk-in): who sold it, the appointment's service at its booked price, more services, products (one without a price asks for it, and products that didn't load say so, with Try again) and amounts, and Cash or Other ("Squire, Zelle, Cash App…"), each confirmed first ("Record a $63 cash sale for Carlos?"). The total and how they're paying stay at the bottom of the panel, below the items, which scroll: what + Service or + Product opens comes into view above them, never under them (on a short screen, a phone held sideways say, the whole panel scrolls, with Close at the top). The sale goes to `POST /api/owner/sales` with an `Idempotency-Key` kept until the sale is recorded, also when its ticket is closed and the same sale rung up again, so a retry never records it twice. Card payments stay on the iPhone, with Tap to Pay. A sale is voided from Today's sales, or from its appointment (with the sale from the day it was sold), asking first, with a reason if the owner wants one; a card sale's refund is done in the Stripe Dashboard, and the question says so.
- **Analytics**: the whole shop or one barber; Today, Week (from Monday), Month, Year, or Custom dates. Total sales with the change from the same number of days just before, named ("Down 6% from Oct 28 – Oct 31"), split into services, products, other and fees; the top sales barber; daily sales as stacked bars (by month for a year; one stop for the keyboard, the arrow keys move between the columns), or for Today each barber's sales; the leaderboard (sales, services, products or clients served, the top three with medals); top services; products sold; and the productivity tiles, each with what it means. Every chart has its table one click away. It's all as the server computes it (`GET /api/owner/analytics`, defined in `docs/analytics.md`), refreshed every 30 seconds while it's on screen, with "Live · Updated 12:30 PM" (gray, and "Last updated 12:30 PM", while refreshes fail).
- **Products**: add, edit and delete, with a price or none (checkout then asks for one), shown in the client app or hidden, and a photo: whatever the owner picks is drawn again in the browser as a JPEG of at most 1,600 pixels (640 in the demo, which keeps it in the browser) and under 4 MB before it's sent.
- **Settings**: card payments (Connect Stripe, which leaves for Stripe's own pages and comes back to `/business/settings?stripe=…` (`returnTo: "web"`), and the account's state); no-show protection, as the iPhone app sets it (the fee as a share of the service or a flat amount, never more than the service's price, late cancellations and their window, examples, and the notice clients see, which says the fee "may be charged"); this computer's session; the other computers signed in, each signed out on its own or all at once; and how to put Izzy Clipz Business on this phone or computer.
- **Its own app.** `business/index.html` links `/business/manifest.webmanifest`: Izzy Clipz Business ("IC Business" on a Home Screen), scope `/business/`, starting at `/business/today?source=app`, with its own icons (the logo with a red Business tag). Installed, it opens the owner's area in its own window, apart from the clients' Izzy Clipz app. `/business` (what the iPhone app tells the owner to type) becomes `/business/` as soon as it opens, so the page stays inside that scope. The pages ask search engines not to list them.
- **The service worker** opens every `/business` address from that page, also offline, where a line says the owner's area needs the internet. Nothing from `/api/owner`, sessions or computer codes is ever kept: they always go to the network.
- **Hosting**: `/business` and everything under it is the Business page (`../vercel.json`, and `vercel.json` here for the demo).

## The demo version

`npm run build:demo` (or `VITE_DEMO_MODE=1 vite build`) builds the same site into `dist-demo/`, to publish before the shop's server is ready. The normal build is untouched by it.

- Its API calls are answered in the browser by `src/demo/api.ts`, which has the API client's own interface: the build puts `src/demo/backend.ts` in place of `src/api/backend.ts`, so the demo has no code that calls `/api`, and the normal build none of the demo's.
- Like the apps' `FakeShopAPI`, it uses the shop's real catalog (the server's own `data/catalog.json`, built in), works out the open times from the shop's hours, slot interval, lead time and 60-day window on the shop's clock (`America/Los_Angeles`, the real time, so daylight saving changes are handled), and gives every barber two or three sample bookings each open day, the same every time, so some times are taken. Bookings and cancellations follow the server's rules (a retry with the same manage token gets the same appointment back, 3 upcoming appointments per number, cancelling until the start, the late-cancellation question for a booking with a card on file) and are kept in `localStorage` (`izzy.demo.v1`), so they're still there after a reload. No-show protection is off, as on the server until the owner turns it on: no card, no Stripe. The reviews are samples ("Sample reviewer A") with no rating.
- Home, Review, Get the app, the booked page and My appointments say "Demo version: bookings aren't sent to the shop. To book for real, call (442) 341-3053." The booked page is "Demo booking made", with that line right under its title (on a phone's first screen, the Add to Home Screen bar showing or not), and its calendar file is "DEMO, not booked: …", says the shop doesn't have it, and sets no reminder. On My appointments the line is above the bookings, on a phone's first screen, and cancelling one says "This is the demo: nothing was sent to the shop." where the real site says "The shop sees it right away.", in the question and once it's cancelled.
- Your details (booking step 4) says the details stay on this phone (or computer) and aren't sent anywhere, in its subtitle and its privacy line, and Remember me says nothing of a saved card: the demo never asks for one.
- Reviews says the reviews are samples ("The real site shows the shop's reviews from Google, and links to Yelp."), and shows them under "Sample reviews", with links to the shop's real reviews: none of Google's labels, attribution or terms, which belong to Google's own reviews.
- Offline it all still works (it needs no network), and the line under the nav says so: "You're offline. The demo still works. To book for real, call the shop: (442) 341-3053". My appointments lists its bookings offline too.
- It keeps no client's name, number, email or note: its store (`izzy.demo.v1`) has each booking's appointment, manage token and a scrambled code of the number (for the 3-per-number rule), and "Forget me" on My appointments clears it. It lists its bookings under its own key (`izzy.demo.appointments.v1`) and carries none into an app on the Home Screen: they only exist in the browser they were made in. The real site, should it ever open at the demo's address, forgets both.
- **Izzy Clipz Business in the demo** opens with one button (no code): a sample shop with the real catalog and team, sample clients ("Ruben Sample"), eight weeks of history and two weeks ahead, the same every time for a given day, five sample products and a sample iPad signed in. Its answers come from `src/demo/owner/api.ts` (the build puts `src/demo/owner/backend.ts` in place of `src/business/api/backend.ts`), which follows the server's rules (checking out, voiding, statuses, the no-show fee with its 7 days, its end time and its completed visits, products, no-show settings, computers) and keeps everything in `localStorage` (`izzy.demo.business.v1`). Its analytics are worked out from its own appointments and sales with the same definitions as the server (`src/demo/owner/analytics.ts` and `facts.ts`, kept equal to the server's code by `tools/analytics-parity.test.ts`, and checked by hand against `docs/analytics.md` in `src/demo/owner/api.test.ts`), so a sale shows in Analytics at once. Connect Stripe pretends the connection after a moment and says no real account was connected; until then a no-show fee is refused, as on the server, and the card ending in 0002 is declined. Every page says "Demo version: sample data, nothing is sent anywhere.", it works offline, and Settings has "Reset the demo" to bring the sample shop back.
- `dist-demo/vercel.json` (a copy of this folder's `vercel.json`, which Vercel reads directly when it builds the demo from Git with `server/web` as the root) hosts it as a static site of its own: files first, the page for every other path but `/api/` and `/assets/`, `/sw.js` with `Cache-Control: no-cache`, the manifest as `application/manifest+json`, a year's caching for `/assets/`, `X-Robots-Tag: noindex` (so the demo doesn't show up in searches for the shop; its own `robots.txt` lets search engines read that), a Content-Security-Policy (only its own scripts, styles, fonts and images, never in a frame) and a Permissions-Policy (no camera, microphone, location or payments). Deploy the folder as it is, with no build step.

### Publishing the demo, and its way out

Once someone opens the demo, its service worker keeps opening it from its own copy, and an app added to a Home Screen stays tied to the address it came from. Deleting the demo's project changes neither: the browser can't find a new version, so it keeps the one it has, and the demo goes on taking bookings that go nowhere. So decide where the real site will live before publishing the demo:

1. **Best: publish the demo at the address the real site will have** (the shop's own domain, or the `*.vercel.app` address the real site's project will use). When the shop's server is ready, serve the real site at that same address: deploy it to that project, or move the domain to the server's project (Vercel can move a project's domain to another). Every browser and installed app then finds the real site's new `/sw.js`, shows "A new version is ready · Reload", and becomes the real app with a tap. The demo's bookings stay behind: the real site never lists them and forgets them.
2. **Otherwise, retire it:** never delete the demo's project while people may have it. Once the real site is live elsewhere, run `DEMO_MOVED_TO=https://<the real site> npm run build:retired` and deploy `dist-retired/` to the demo's project in its place, as it is. Its service worker takes the demo's place in every browser the next time the demo is opened (no tap needed), clears the demo's files, steps aside and reloads the page; every address then shows "Izzy Clipz has moved." with a button to the real site's Get the app, and that page clears what the demo kept in the browser. Keep it deployed for a few months, for phones that open the demo rarely.

## What the browser keeps

- `localStorage` `izzy.appointments.v1`: each appointment booked here, with its manage token (what My appointments lists and cancels with), until 30 days after it ended. Not the client's name, number, email or note.
- A cookie, `izzy_appointments`: the id and manage token of each of those appointments (ten at most, until 30 days after they ended), only so an app added to an iPhone's Home Screen can bring them in (see [The web app](#the-web-app)). The server never reads it; "Forget me" clears it.
- `localStorage` `izzy.details.v1`: name, number and email, only with "Remember me on this phone" (or computer).
- `izzy.card.v1`: the card token, the card's brand and last four digits, and the number (E.164) of the client who added it, in `localStorage` with "Remember me", otherwise in `sessionStorage` until it's booked.
- `sessionStorage`: the booking in progress (`izzy.booking.v1`, so a reload or the trip to Stripe's card page doesn't lose it), the card checkout in progress, the last booking for "You're booked", and whether this tab's visit is counted (`izzy.visitCounted.v1`).
- `localStorage` `izzy.visits.v1` (how many visits) and `izzy.installHint.v1` (the Add to Home Screen bar was closed, or the app installed): only for that bar.
- The service worker's caches: `izzy-app-<version>` (this version's files; older versions' go once a new one takes over) and `izzy-catalog-v1` (the shop's public catalog). Nothing personal.
- `localStorage` `izzy.business.session.v1`: Izzy Clipz Business's session on this computer: its token, and its id, name and dates for Settings. Never the owner key. Sign out, the server turning the session down, or its 30 days running out, removes it.
- `localStorage` `izzy.business.lastBarber.v1`: the barber picked last for Sold by on this computer (the barber's id, nothing else), so the next walk-in starts with him, as the app does.
- In the demo only, `localStorage` `izzy.demo.appointments.v1` (its list, in place of `izzy.appointments.v1`, and no cookie) and `izzy.demo.v1`: the bookings made in it, as the shop's server would keep them but with no name, number, email or note (a scrambled code of the number instead), until 60 days after they ended. "Forget me" clears both. Izzy Clipz Business keeps its sample shop in `izzy.demo.business.v1` and its session in `izzy.demo.business.session.v1`; "Reset the demo" starts the sample shop again. The real site, opened at the demo's address, forgets all four.

Each of these ends when the Privacy Policy's table says it does: the appointments go 30 days after each one (when the site next opens), the booking in progress once it's booked, and in the demo "Forget me" and "Reset the demo" clear what it kept. `e2e/legal.spec.ts` checks that the browser keeps nothing else, and that the real site's only cookie is `izzy_appointments` (the demo sets none).

A computer can be shared, so "Remember me" starts off unless this computer already remembers the client, a saved card is only ever offered to the number that added it, and a booking that's done (or a new one) doesn't carry the last client's details or note. "Not you? Forget me on this computer" on Your details, and "Forget me on this computer" on My appointments (each naming the device), clear what's kept here; the appointments stay booked with the shop. They also delete the saved card at the shop (see [The card on file](#the-card-on-file)).

## The card on file

When the shop's no-show protection needs a card, Review's "Add a card" makes a card token, calls `POST /api/cards/checkout` with `returnTo: "web"` and `X-Card-Token`, keeps the token and the booking in this tab, and sends the browser to Stripe's page. Stripe comes back through the server to `/book/card-return?status=saved&session_id=…` (or `?status=cancelled`); that page saves the card with `POST /api/cards` and goes back to Review, which then shows "Visa •••• 4242 · Change" and lets the client book. Only the card page this tab opened last is saved (an older one, reached through the browser's history, says so), and "Try again" shows only when trying again can work (the shop wasn't reached, or asked to wait). If the server answers `card_required` anyway (the shop turned protection on meanwhile), Review checks the policy again and forgets only a card it sent.

The card's key exists only in this browser, so whenever the site lets go of it for good, it asks the shop to delete the card (`DELETE /api/cards` with `X-Card-Token`, `src/lib/cardRemoval.ts`, sent with `keepalive` so it still reaches the shop if the tab closes right after), and forgets the key here whatever the answer:

- **"Forget me" and "Not you?"**: the server deletes the card at Stripe now, or, while a booking still needs it (it's upcoming, or can still be charged a fee within 7 days), as soon as none does. The page says which in one plain line (on My appointments in the server's own words: "Your saved card is deleted. It can't be charged any more." or "Your card will be deleted as soon as your appointments no longer need it."). If the shop can't be reached (tried twice), it says to call the shop to have the card removed. This is what makes the Privacy Policy's and the Cancellation & No-Show Policy's "Forget me on our website" remove a saved card.
- **Right after a booking made without "Remember me"**: the server can't see the box, so the site asks it then. The server answers "scheduled": it keeps the card only while that booking can still be charged, then deletes it, which is how "without Remember me, the card is used only for the booking you saved it for" stays true. The same goes for a remembered card the client chose not to keep this time.
- **A card nobody could use any more**: one replaced by a new card ("Change card"), another client's card dropped on Your details, or one the server turned down for a booking.

The demo never saves a card; its in-browser API answers `deleteCard` as the server does for a key with no card (404), without a request.
